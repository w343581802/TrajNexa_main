# 36｜M5 统一多模型、可编辑提示词与评测体系（规划 V0.1）

> 日期：2026-11-01
>
> **状态：产品与架构决策已确认；本文是实施规划，不代表模型管理 UI、API 或持久化已实现。**
>
> 适用：TrajNexa_main（主系统）及独立 Rebucca 推理/评测环境。TrajNexa_Map 不承载此功能。
>
> 决策来源：Rebucca 实测适用性反馈；小模型和视觉大模型均须多选；**大模型提示词必须能够在界面上编辑、试运行、比较、保存版本并回退，不依赖代码发布**。

## 1. 冻结的架构原则

1. **模型中立**：检测、分类、ReID、实例分割、视觉语言模型等统一注册；不将 Qwen3-VL、D-FINE、YOLO、Ollama 或 Rebucca 写死为唯一后端。Rebucca 是优先复用的多模型/推理与测试体系，但 TrajNexa 保留独立的模型注册、调用契约和证据归属。
2. **多模型并存**：同一任务支持选择一个模型、多个模型并行对比或“检测 → 原始分辨率 ROI 裁剪 → 视觉模型描述”等串联方案。人员与车辆可配置不同默认工作流。
3. **提示词是可配置资源，不是代码常量**：每种分析任务可创建多个 Prompt 模板；按模型覆盖或继承；通过界面编辑、克隆、验证、试运行、发布、回退。
4. **模型版本 × Prompt 版本 × 推理参数共同决定一次实验**。任何模型/提示词调整不覆盖已经产生的结果或人工复核记录。
5. **原始证据不可修改**。检测框、属性描述、置信度及跨镜头关联均是候选；模型冲突、低画质、不确定与拒判必须可见；不得自动确立身份或填补无观测轨迹。
6. **研发 Demo 与正式部署分离**：Demo 不增加登录/RBAC/授权勾选的使用阻力；正式部署仍需访问控制、密钥保管与审计，不得将未经保护的本地 API 暴露公网。

## 2. M5 子模块与职责

| 子模块 | 主要能力 | 明确边界 |
|---|---|---|
| M5a 模型目录 | 注册、启停、模型版本、推理地址、能力标签、权重哈希/许可、健康状态 | 不把模型连接详情写入轨迹事实 |
| M5b 推理适配层 | Rebucca/ONNX/OpenVINO 与 OpenAI-compatible/Ollama 等 Provider Adapter；统一请求、结果、错误与超时 | 不直接依赖上游报警规则/Django ORM |
| M5c **Prompt 工作台** | 模板管理、在线编辑、版本、参数、变量预览、试运行、差异对比、回退 | 不需修改 Python/前端代码来调整提示词 |
| M5d 模型实验室 | 同图/同视频段选多个小模型、大模型、Prompt 版本对比；速度/召回/误检/属性正确率记录 | 没有真值时只报告候选数量，不伪称“准确率” |
| M5e 任务工作流 | 可配置检测器→裁剪→VLM→人工复核，人员/车辆按任务选用不同组合 | 不允许模型输出直接确立同一目标身份 |
| M5f 运行留痕 | 输入来源、哈希、模型/权重/参数、完整 Prompt 快照及哈希、输出和失败状态 | 不覆盖历史运行；不把测试结果自动入正式证据 |

## 3. Prompt 工作台：必须实现的交互

**入口：AI 模型实验室 → 提示词管理**。界面建议左右布局：左侧任务与模板列表；中间编辑器；右侧变量、结构校验、原图/ROI 与输出预览。

**基础功能（首批）**：

- 任务维度：`person_attributes`、`vehicle_attributes`、`vehicle_type_review`、`scene_context`、`candidate_review`、`camera_osd_reading` 等；任务类型可扩展，不被固定列表锁死。
- 模板字段：显示名称、适用任务、语言、说明、启用状态、变量说明、默认输出 schema、关联模型配置。
- 可编辑内容：`system_prompt`、`user_prompt_template`、可选 `few_shot_examples`、输出格式说明、温度、最大输出 Token、超时等；模型不支持的参数要显示不支持而不是静默接受。
- **模板级默认 Prompt → 具体模型覆写 Prompt → 单次实验临时覆写**；每次运行必须展示实际生效的合成结果和所用变量。临时覆写默认仅影响本次实验，不修改已发布配置。
- **保存草稿 / 复制模板 / 发布版本 / 查看差异 / 一键回退**；发布的新版本只作用于后续运行，旧结果绑定旧版本。
- **试运行**：选择一张已登记的测试图片或 ROI，在同一个实验界面中对比两个模型或两个 Prompt 版本；展示原始输出、解析后的属性、不可解析/拒判原因、时延。
- **显式变量**：支持 `{{task_type}}`、`{{object_category}}`、`{{image_quality}}`、`{{roi_context}}` 等有来源且经校验的变量；禁止任意模板表达式或执行脚本。模型输入的 OCR 文本和画面内容必须被标记为**不可信数据**，不能提升为系统指令。
- **结构化输出合同**：针对候选属性要求明确 `unknown` / `uncertain` / `not_visible` 等状态；JSON/schema 校验失败应标记为失败或待人工复核，不得虚构默认属性。
- **安全与证据约束不可由任务 Prompt 取消**：用户可编辑描述方式、识别粒度与字段，但系统层面的原件留存、案件绑定、禁止自动身份确证、失败不等于无目标、日志留痕等必须由应用逻辑保证，而不能只依赖 Prompt 字面指令。

**编辑体验**：带行号的多行编辑器、字符/Token 预算提示、参数说明、未保存修改提示、预览实际填充后的 Prompt；不要求用户写 Python/JSON 才能修改自然语言描述。

## 4. 数据结构草案（不是已存在的数据库表）

| 实体 | 核心字段 |
|---|---|
| `ModelProvider` | `id, kind, endpoint_ref, capabilities, health_status`（凭据独立安全保管） |
| `ModelDefinition` | `id, provider_id, model_id, family, version, task_capabilities, weights_sha256, license_ref, enabled` |
| `PromptTemplate` | `id, task_type, name, description, output_schema_ref, active_revision_id` |
| `PromptRevision` | `id, template_id, revision, system_text, user_text, examples_json, params_json, content_sha256, created_at, change_note` |
| `ModelProfile` | `id, task_type, detector_model_id?, vlm_model_id?, prompt_template_id?, prompt_revision_id?, overrides_json` |
| `ModelRun` | `id, case_id?, source_media_ref, source_sha256, roi_ref?, model_definition_id, prompt_revision_id, effective_prompt_sha256, params_snapshot, output_raw_ref, output_parsed, duration_ms, status, error_code, created_at` |
| `EvaluationRun` | `id, dataset_revision, profile_ids, sample_ids, human_ground_truth_ref?, metric_summary, created_at` |

要求：按运行保存生效 Prompt 的**不可变快照或可验证内容哈希 + 版本引用**，防止修改模板后丢失当时的识别依据；敏感原文按访问范围管理。

```json

  "task_type": "vehicle_attributes",
  "model_id": "registered-model-id",
  "prompt_template_id": "vehicle-template-id",
```

## 6. 第一批预置模板（可编辑、可复制）

| 模板 | 推荐输入 | 输出重点 |
|---|---|---|
| 人员外观 | 人员原图 ROI + 少量上下文 | 衣服、裤子、携带物、运动姿态；不可见即未知 |
| 车辆外观 | 车辆原图 ROI + 少量上下文 | 车身颜色、可见车型线索、车顶/车尾/货厢特征、遮挡；无法确认车型时拒判 |
| 两轮车复核 | 检测器候选 ROI | 自行车/摩托车/电动车的可见区别；仅凭模糊画面不强判 |
| 画面上下文 | 有限关键帧 | 目标附近人车、可见方向、遮挡等场景事实，不建立独立无关人员档案 |
| OCR 复核 | 裁剪角标 | 字符串与模糊/无法读出状态，不补造日期和号码 |

初版应包含“同一模型不同 Prompt”和“同一 Prompt 不同模型”两个对照视图；模型争议不得通过简单投票升级为已核实事实。

## 7. 实施顺序及验收

1. **M5-P0｜冻结模型输出与证据契约**：检查当前 TrajNexa 的硬编码 `DETECT_PROMPT` / `FEATURE_PROMPT`，梳理 Rebucca 的模型注册与参数机制。实现 Prompt 版本对象但先不替换现有生产调用。
2. **M5-P1｜Prompt 工作台最小闭环**：UI 编辑 → 校验 → 保存版本 → 选择图片/ROI 试运行 → 查看原始/解析结果 → 发布或回退。禁止仅修改前端文字却仍调用旧 Prompt。
3. **M5-P2｜统一模型注册与 Adapter**：先支持一个 Rebucca 检测器及两个本地视觉模型；逐步添加其他 OpenAI-compatible 服务。模型连接参数不得混进 Prompt。
4. **M5-P3｜同样本评测**：相同车辆、人员、夜间、红外、遮挡样本下比较模型和 Prompt；报告按类别拆分的漏检、误检、错误描述、拒判、延迟、显存/内存。
5. **M5-P4｜任务级 Profile**：分别配置人员/车辆工作流；只将经过人工确认的观察提交至既有案件证据链。

**必须验证**：保存新 Prompt 后试运行确实使用新版本；重启后版本仍存在；发布/回退互不篡改历史；无效变量/非法输出明确失败；模型离线/超时不会伪装为无目标；结果能反查原图、模型、参数和 Prompt；实验数据不自动生成跨镜头身份确认。
