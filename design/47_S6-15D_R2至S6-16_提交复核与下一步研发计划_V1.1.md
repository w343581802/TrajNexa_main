## 0. 本次技术决策

**调整顺序为：修正调度/证据与转移图语义 → 真实视频一跳贯通 → 数据集与现场核实 → 二跳与多轮回放 → 有数据后再决定预测模型。**

1. **保留** S6-15C FOV 规划器为默认空间候选基线；不因为单个样本改权重；理论 FOV 与 GIS 仍为软先验。
2. **保留并补强** `m6_camera_scheduler.py`；它是优先实现的关键模块，但目前只达到调度原型级别，不能把“窗口内检测到任何人”当成目标候选。
3. **保留** `m6_window_analysis.py` 作为现有 D-FINE/ByteTrack 的薄适配；解决时间来源、帧空缺、分段连续性和实际成本入账。
4. **接受 R1-A 负结果**：真实快照上 2-1 从第 2 退至第 4；代码保留作实验基线，不接默认路径，不进行针对单例的调参；当前 `direction_quality=unknown`，R1-B 多假设/Stone Soup 暂缓。
5. **保留 R2 转移图** 作为可撤销的观测关系记录，不作为预测概率或排序增益的正式依据；优先修复待审核记录混入统计、样本独立性、完整撤销传播等问题。
6. **暂缓 R3 融合**。R1 当前是负收益，R2 只有一条核实关联；现在融合的结果主要反映人为权重而非可验证的新信息。
7. **提前做 S6-16 的数据准备**：三路 Map 绑定仍 `pending_human_review`；1-1 15:00:03.8 仍 `candidate`；没有独立真值就不宣称三镜头追踪已实现。
8. **接口研发期可调整**：只把身份确认、时钟/空间来源、撤销、数据审计等语义作为硬约束。轻量输入输出对象随实际运行反馈增改，不冻结最终 API/数据库架构。

### 1.1 需要更正的成本表述

仓库 `design/44` D.44 与 `design/assets/m6_s6_15_d123_compare.json` 的 215 / 215 / 140 是**固定窗口/回放条件下的调度入账帧数**。当前 `CameraScheduler.submit()` 用分析窗口时长和配置帧率计算 `decoded_frames`，并未采用 `m6_window_analysis.analyze_window()` 的 `frames_decoded`。因此可表述为：**D3 在该调度回放中的帧预算低约 35%；实测端到端成本收益尚需验证**。

此外 1-1 首位的 FOV 重叠是实际模型视域的几何关系（D.45 记录顶点重叠比例约 0.812），不是计算程序虚构的重叠；但**几何重叠本身不足以证明它应优先于 2-1 执行正向查询**。不要随意增加重叠惩罚或同杆奖励以匹配单个案例。

## 2. P0 代码修正清单（优先于新模型）

### P0-A：调度器不能以“检测到人”替代“指定目标候选”

**现状**：`m6_camera_scheduler.py::submit()` 遇到 `status="ok"` 且任意 `tracks` 即切至 `needs_review`。这只能表明窗口内检测到了目标类别（行人），不能表明已找到了用户指定的目标。

**改动**：增加轻量的候选检索适配（可用 `m6_target_candidate_adapter.py`，也可复用已有 ReID 入口），明确以下层次：

`WindowObservation(tracks)` → `TargetCandidate(supports/conflicts/unknown)` → `ReviewDecision` → `ConfirmedAssociation`。

- 一般人轨迹不自动触发“目标已发现”；可缓存 Tracklet 并继续其他镜头或时间段。
- OSNet 排序、视觉属性、时空支持只产生 `candidate/needs_review`；高相似度不能自动成为 `human_confirmed`。
- 人工拒绝或证据不足时，能够恢复当前摄像头未处理区间及其他镜头队列；不能因为 `needs_review` 被跳过而丢失搜索。
- `confirm_hop()` 不能仅凭传入 `human=True` 就创建正式可信关联；正式流程由具备可追溯证据引用的人工审核事件调用。研发模拟可以保留，但单独标记 `simulated_review`。

**测试**：任意人员 30 条但目标缺失；Top-1 高相似误匹配；待审暂停/切换/恢复；候选被否决继续搜索；真正确认后才推进主链。

### P0-B：窗口分析时钟、分段跟踪和成本实测

**现状**：`m6_window_analysis.py` 每窗口创建新 ByteTrack；只有检测到人员时才调用 `adapter.update()`；没有 OSD 锚点仍可返回 `status="ok"`；返回时间为相对秒，并直接读取跟踪器私有 `_tracks`。

**改动**：

- 统一使用**每路实际首帧 OSD/PTS 锚点**与可追溯时钟质量；缺少绝对时间映射时，不得当成可验证跨镜头候选时间（可仍保存局部 Tracklet）。
- 对每个已成功解码帧推进跟踪器，包括无人检测帧；失败解码单独记录。
- 分段延续时优先传递跟踪状态，或提供去重和可核查的跨段 Tracklet 拼接；不要将每段 `track_id=37` 假定为同一持续轨迹。
- 通过公开适配方法获取轨迹，不长期依赖 `_tracks` 私有字段。
- 成本 `frames_requested / frames_read / frames_decoded / detector_frames / reid_calls / vlm_calls / wall_time` 分列；调度预算可使用估算值，但实测账本必须用执行返回值。
- 录像资源索引未配置/查询失败应返回 `unknown/unavailable`，不能默认为整段录像存在；Map 的 `has_video` 不作为录像可用依据。

**测试**：6 秒切片边界连续过人；连续空帧；无 OSD 锚点；错误帧目录；重复窗口缓存；实际帧数与计划帧数不同；录像索引异常。

### P0-C：转移图只以可靠核实数据参与统计

**现状**：`usable()` 对 `pending_review` 返回 True；`support_count()`/`transition_time_summary()` 可能统计待审记录；`source_track` 只是局部编号，不保证跨录像、跨目标唯一；5 条未校时时差可以给出中位数；撤销只处理一层。

**改动**：

- 明确 `reviewable()`、`is_human_confirmed()`、`eligible_for_statistics()` 等不同语义；统计时只采用符合条件的已确认关联。
- 一条样本至少关联稳定的 `target_id`、源/目标 `camera_uuid`、`recording_id`、`tracklet_id`、`association_event_id` 和人工确认来源；在绑定待审时继续标 `exploratory`。
- 去重依据应是独立**确认转移事件/目标经过事件**，不能仅用 `source_track`，也不能将同一人相邻帧当作多个样本。
- 未完成跨摄像头校时时只统计“名义 OSD 间隔”，不能产出可信物理通行时间分布。`min_support=5` 是当前研发门槛，不能解释为已有 5 条便可估精确概率；还应考虑不同录像覆盖范围与样本选择偏差。
- 撤销改为沿依赖图递归/迭代传播到所有后代，支持分支、循环防护、幂等，保留审计日志；同时同步撤销依赖该关联的调度假设/TargetProfile 版本。
- JSON 文件保留测试 fixture 作用；实际任务逐渐增多后再评估事务性持久化，不急于定最终表结构。

**数据清理**：`design/assets/m6_s6_15_transition_graph.json` 的 `2-1#37 → 1-1#225` 是 `pending_review` 派生样例，缺少当前真实证据支持，而且 1-1 #225 在旧实验属于青衣带小孩骑手案例。将其移到独立 `synthetic_fixture`，或明确 `synthetic=true` 并禁止进入真实任务和统计；正式记录仅保留经人工核查的 `2-2#111 → 2-1#37`，但其地理绑定与时钟仍未校准。

**测试**：5 条待审≠可学习；两路相同 `track_id` ≠一条样本；重复确认事件不重复计；A→B→C→D 多级撤销；撤销后预测和主链不继续使用旧状态；模拟样本不入统计。

### P1-D：预测器工程质量（本批不扩展算法）

`m6_motion_predictor.py` 的质心与外接圆是粗近似，不应将 `plausible=False` 当成真实不可达；代码和负结果保留作基线。后续若确有使用，才替换为成熟几何库、重审坐标单位与空间误差。当前无需引入 Stone Soup / Trajectory Tensors / Valhalla。

## 4. B1 具体实现任务：最小真实一跳执行链

建议保持模块化单体，轻量集成链如下：

```text
2-2 已确认观测 / TargetProfile V1
    ↓ Map-only Spatial Planner（不修改当前排序）
PredictionCandidate 列表（1-1 排第一，2-1 排第二）
    ↓ CameraScheduler 选镜头、选窗口、核录像资源
WindowAnalysis → D-FINE N → ByteTrack → Tracklet
    ↓ TargetCandidate 选择（OSNet、多帧证据，可按需 4B）
CandidateEvidence：supports / conflicts / unknown
    ↓ 模拟审核或真实人工审核（明确区分）
若被拒绝：恢复剩余窗口/下台摄像头
若人工确认 2-1#37：更新 TargetProfile V2，记录转移证据
    ↓
本轮结束，下一轮从 2-1 新状态重新规划
```

推荐按从低到高的集成级别做四个验证：

1. **纯逻辑**：使用固定帧/固定 Tracklet，校验调度状态机，不触发 GPU。
2. **真实窗口感知**：使用真实冻结帧，验证检测/跟踪、OSD 映射与实际帧数。
3. **真实候选比对**：对窗口 Tracklet 用当前 OSNet 排序；错误候选不自动确认；人工审核后才能入主链。
4. **真实一跳回放**：在相同录像条件下比较 batch / serial / segmented 的 `frames_decoded`、检测调用数、GPU 时间、目标召回和错误停止。不能将模拟“目标命中”混入真实成本报告。

至少固定以下回归情形：Top-1 只有其他人员；Top-1 检测漏检；Top-2 有目标且候选排名不一定第一；Top-1 人工否决后继续；录像时间段不可用；无可靠 OSD 映射；同杆反向独立通道；分段重叠与去重；预算中断/恢复；人工撤销 B 后 C 派生候选失效。

## 6. 通过标准与禁止的表述

### B1/B4 基础通过

- 实际解码轨迹和成本由真实执行返回，模拟/预测/真实成本指标分开。
- 检测到其他行人不会误报“已找到目标”；候选只进审查，不能自动确认。
- Top-1 不可靠时可以继续 Top-2，窗口不足时可在预算内扩展，不会以 `no_valid_observation` 推导目标缺席。
- 已确认一跳可以更新 TargetProfile 并继续规划；未确认分支可隔离、撤销。
- 原始录像、模型、时间映射、Map 快照及审核决定均可追溯。

### B2 基础通过

- `pending_review`/`synthetic` 不进入计数与时间统计。
- 不会将时钟未校准的名义 OSD 差解释成真实移动时长。
- 依赖链多层撤销及重复撤销后状态一致。

### 暂时不能宣称

- **不能说** R1-A 优于原规划器：当前记录是 2→4 的负结果。
- **不能说** D3 已在真实 GPU 任务中减少 35% 计算成本：尚需以实测帧数及推理开销复核。
- **不能说** 一条转移构成可靠转移概率或物理通行时间分布。
- **不能说** 三镜头连续追踪成功：当前第三镜头没有独立确认真值。
- **不能说** Map 数据已被现场完全验证：绑定和模型 FOV 仍有不确定性。

## 7. 后续是否恢复 R1-B/R3 的明确触发条件

只有出现可检验的新信息时，再投入新预测算法：

- 获得可靠的 `world_motion`、出入画区域标定，才重新比较“方向性多假设预测”与现有 FOV 基线；
- 积累多条**独立、已确认、时钟质量可说明**的转移及充分任务覆盖记录，才研究转移时间分布和可学习排序；
- 至少具备多个目标、多个摄像头转移和独立保留的评测集，才研究 R3 融合或 Stone Soup/MCTF 的部署价值；
