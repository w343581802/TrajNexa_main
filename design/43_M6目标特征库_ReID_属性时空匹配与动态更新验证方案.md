# 43｜M6 目标特征库 × ReID × 属性 × 时空 × 动态更新：验证方案 V0.1

> 决策日期：2026-11-01。性质：**技术验证 Demo 方案，尚非功能验收报告**。
> 本文先于代码实施；仅当有真实样本和可重跑结果时，才把“规划”改为“已验证”。
> 业务目标：调查人员提供一张目标照片，TrajNexa 查找归属录像，观察该目标在同一录像中的连续帧，补全可信的可见外观线索；再在其他已登记、获授权的多个摄像头录像中进行**候选检索和轨迹还原**，而不是仅提示核查哪些摄像头。
> 人工核实前只称“疑似同一目标/待核实候选”，不得自动确认真实身份。

## 1. 五模块职责

| 模块 | 输入 | 输出 | 首批验证 |
| --- | --- | --- | --- |
| **目标参考特征库 TargetProfile** | 用户给定照片 + 手动框 + 来源证据 | 不变的初始目标锚点、多视角参考图、人员/车辆/人车关系、模型版本与可见属性；人工确认记录 | P1 在模型测试内先使用**临时内存 profile**，不提前建正式数据库 |
| **ReID 视觉匹配** | 原图像素 ROI + 已安装的类型合适的 ReID 权重 | L2 单位向量、候选 cosine 排名、相似度及来源 | 人员 OSNet 已移植，先做 A↔B 单图候选检索；车辆 ReID 不能借用人员 OSNet |
| **属性匹配** | VLM 结构化可见属性 + 质量/遮挡/可见性 | 一致、矛盾、未知的解释性证据 | 紫色衣服、尾箱、侧挂粉色物品等；不把“未观察到”当“确认不存在” |
| **时空约束** | 来源摄像头、角标时间来源/校验程度、相机方位、路网可用性 | 可到达性区间、物理不可能冲突或“未知” | P3 才接；缺失路/未覆盖视野不得作否定证据 |
| **动态特征更新** | 已确认连续帧/摄像头候选 + 原始目标锚点 | 版本化候选/确认池、增加的参考模板、撤回与审计 | P2 同视频多帧开始；跨镜头未确认候选**绝不自学习** |

### 1.1 不是“让 YOLO 学会识别这一个人”

- YOLO、D-FINE **只负责在每帧发现候选**；不能直接用一段中文属性替代权重训练，也不能把检测置信度当同一目标概率。
- 人员 ReID 用 **Person OSNet**；车辆使用另行验证的 Vehicle ReID；骑乘组合是**人员、车辆、物品及同时出现关系**的联合观测，不应整体归成一个新 YOLO 类别。
- VLM 以低频关键帧描述；ReID 向量适合批量计算；交通时间/摄像头路径用于候选约束。
- 候选检索与身份确认严格分开：排序前几名≠确认身份；相似度不解释成百分比身份概率。

### 1.2 骑乘人车示例

目标初始图：骑手上衣偏紫，当前帧**未见头盔佩戴**；疑似电动两轮车、有尾箱、右侧粉色悬挂物疑似头盔，尾箱上方疑似绑有物品。按画面可见情况分开记录：

```json
  "reference": {"anchor_id": "initial_manual_roi", "verified": true},
  "entities": [{"key":"rider","type":"person"}, {"key":"vehicle","type":"two_wheeler"}],
  "relations": [{"subject":"rider","predicate":"riding","object":"vehicle","time_scope":"observed_frame"}],
  "attributes": [
    {"entity":"rider","key":"upper_color","value":"purple","visibility":"visible","certainty":"likely"},
    {"entity":"rider","key":"helmet_worn","value":"not_seen","visibility":"head_visible","certainty":"likely"},
    {"entity":"vehicle","key":"rear_box","value":"present","visibility":"visible","certainty":"likely"},
```

## 2. 匹配计算与决策

建议用**逐级召回/重排**，而不是一开始把所有模型的数值简单加权：

1. **检测与单镜头去重**：D-FINE/YOLO → 框 → 局部短轨迹；优先低漏检，保留模型/框来源。图片 P1 暂不做跟踪。
2. **类型一致的 ReID 排序**：固定人员 OSNet 对人员 ROI；车辆需独立向量模型。对两张清晰参考图做多模板 cosine（各模板评分都保留），展示 Top-K。不能把不匹配类型的向量强行比较。
3. **可见属性重排**：按 `match / conflict / unknown` 汇总。只有**相关部位足够清晰且确证不一致**才记冲突；缺视角、遮挡、画质差记 unknown；显著但不确定的“粉色挂物”等为核查线索而非硬排除规则。
4. **时空可行性**：前后镜头的时间窗口、摄像头方向、路网可达区间与估计速度；仅对已校验来源施加硬约束，未核实时间给出范围/不确定标志。
5. **多帧复核与人工裁决**：模糊候选可利用临近同行人/车辆作为时间位置参考，但不把伴行关系直接当身份凭据；VLM 只复核 Top-K 关键帧；证据不足则继续追踪或返回“未能确认”。

**权重/阈值原则：** 人员余弦阈值、车辆余弦阈值、属性权重、时空容忍区间必须从真实正负样本验证中标定，文档**不预设**诸如“0.85 = 85% 同一人”的伪概率。计算排名时保留各维独立分数与冲突列表，避免过早合成为不可解释的一个分值。

## 3. 动态更新防漂移机制

将来源分为：
- **锚点层（immutable anchor）**：用户最初选中的 ROI + 所属案件/录像/坐标（不可被后续推断替换）。
- **可信层（confirmed templates）**：当前录像连续跟踪且经核实、或由人工确认的跨镜头同目标证据，可增加视角模板/高质量局部图；版本+来源可回滚。
- **隔离层（pending candidates）**：单凭 ReID/属性/时空建议的其他摄像头目标，不写入参考向量池，不参与自动再检索的自扩张。
- **否决/撤销层（rejected/revoked）**：保留拒绝原因、模型版本、人工操作，后续分析不得覆盖人工决定（对应契约 C6）。

即使“高分候选”，也不能自动将其属性添加为该目标固有特征。允许对每帧保存**观测**，但提升成目标**参考**需有明确人工复核/可追溯证据。置信度不随重复帧数量无上限增加；同一轨迹的高度相关帧不可被当作独立投票。

## 4. 分阶段验证：先证据、再扩展

### P0-A｜检测器配置与候选准确性（先于 ReID）

当前 `backend/config/detectors.json` 中 `yolo-v5` / `yolo-v8` / `yolo-v26` 三条登记实际指向 D-FINE ONNX 权重，是**类型与权重不符的测试条目**；`dfine-n` 内联标签仅 58 项且与标准 COCO80 顺序从索引 4 起不同。**不得以此配置出具模型召回结论。**

验收：
- 去掉不能工作的伪 YOLO 实例或替换为与算法对应的真实权重；不改用户机器上现有的私有 ONNX 文件。
- `dfine-n` 统一引用 `config/labels/coco80_zh.txt` 的 **80 类正确顺序**；不能因替换中文字符串而改变 class index。
- 保留真正存在的 `dfine-n`、`yolo11n` 配置；若机器缺权重则显示不可用，**不伪造框或自动换文件**。
- 增加纯配置契约测试：禁止伪 YOLO 指向 D-FINE；D-FINE 标签索引与 COCO80 一致；对应权重实际加载/检测另列现场测试。
- 图像 P0 样本必须包括：小/远骑手、两轮车、尾箱、粉色悬挂物、遮挡/夜景，按 **检出/漏检/误检**分开记录。

### P0-B｜CI 测试入口恢复

当前 `.github/workflows/m4-contract.yml` 仍引用移植时删除的旧测试（例如 `test_m4b_detection.py`），导致 `main` Actions 在收集阶段失败。以**仓库实际存在的测试**替换旧文件引用；至少执行 `test_detectors_registry.py`、`test_m5_model_test_api.py`、`test_m5_vision_registry.py`、`test_m4a_observations.py`、`test_m4c_*.py`、`test_architecture_contracts.py`。前端类型检查/构建保持。不得把“CI 通过”描述为“模型效果已通过”。

### P1-A｜ReID 引擎图片链路（先人员）

最小输入：**参考图片 A（人工指明人员 ROI）** + **搜索图片 B（包含多个候选人员）**。
- `ModelTestLab.vue` 下加独立“指定目标相似检索（实验）”区，复用现有图片选择/结果画布模式；只在模型测试页。
- 后端调用已有 `detectors.detect_flat/proposals` 生成 B 的人员候选，校验候选 ROI；调用已移植的 `ReidOnnxEngine.extract_embeddings` 对 A/B 原图裁剪区域提取向量，统一 L2 归一化后按 cosine 降序排序。
- **人员 OSNet 权重**由部署者在服务器本地配置并核验 SHA256；模型缺失时返回“未安装/无法实验”，不得以颜色或 YOLO 置信度伪装 ReID 分数。
- 输出每候选：`proposal/model_id/source_image_sha256/bbox/class/embedding_model_sha256/cosine_similarity/rank`，`identity_established=false`。
- 界面必须展示可解释排名以及原始候选框，**不能直接写案件/目标档案**。
- 单元测试可 mock embedding；至少 1 个真实 OSNet 权重样例需验证：同目标跨视角 Top-1/Top-5、相似外观误报、CPU 性能。

### P1-B｜车辆 / 人车组合

- 验证**专用 Vehicle ReID** 的权重/模型输入协议、许可、性能。仅有 Person OSNet 时不得对车辆输出“车辆 ReID 分数”。
- 骑乘组合需要**独立人框与车框**，同帧关联（位置重叠、运动及稳定关系）先只提供建议，人工可调整。头盔/尾箱等细粒度属性留给 VLM 关键帧核查。
- 使用四组消融对照：人员 ReID、车辆 ReID、人员+车辆、人员+车辆+可见属性；不能把“人车组合”当一个已训练 ReID 类别。

### P2｜单录像连续帧目标档案

- 只读采用已有 `m4_video.fetch_frame` / `overlay_identity.grab_evidence_frame`；从**用户给定图片关联的已登记录像**寻找起始目标，再在同片段前后帧做短时跟踪（ByteTrack 等是待验证可选方案，不是已实现）。
- 关键帧依据清晰度、遮挡、视角差异挑选，避免逐帧请求 VLM；记录帧偏移是 `requested_offset`，并与 `verified_pts` 严格区分。
- `TargetProfile` V1 原型：锚点、confirmed/pending/rejected、多模板向量、属性与来源；先可使用测试会话 JSON，进入真实案件持久化时才新增 Alembic，不能悄悄篡改 M4a `analysis_json` 语义。
- 量化：与初始单图对比，**多帧是否提升 Top-K 命中**，以及错误候选是否导致漂移。

### P3｜多摄像头时空候选与追踪任务

- 一项 `InvestigationTask` 下多项 `CameraAnalysisJob`，本地视频可并行读取、统一推理池限制 GPU 常驻实例；不把“多摄像头并行”理解成“同 GPU 多模型无限并发”。
- 摄像头 ID 来自现有人工目录绑定、地图只读数据；时间保留 OCR/文件名来源与校验程度；路网缺失、角标漂移或无重叠视角时 `spatiotemporal_status=unknown`。
- 输出候选轨迹路径、支持/冲突证据及未覆盖片段；可继续增量分析下一批摄像头直到获得足够清晰证据或明确证据不足，而不是仅输出推荐摄像头。
- **先通过图片与单视频阶段验证**，再创建持久 Job、Checkpoint、重试和取消机制。

## 5. 实验数据与可重跑评估协议

一组样本至少同时有：
1. **正例**：同一主体的不同视角、尺度、曝光、压缩程度；同摄像头/跨摄像头分别标注。
2. **难负例**：相似紫色上衣、同款/同色尾箱电动车、同形粉色挂物、拥挤/相互遮挡场景。
3. **未知**：不清晰到无法确认目标的样本，不能强迫二选一。
4. **视频对照**：初始单帧 vs 同录像多帧 vs 跨相机候选，人工提供“同一/不同/不足以判断”标签，记录来源摄像头与时间信息是否可信。
5. 所有样本仅在有合法授权的本地环境使用；远程视觉 API 发送前必须明确数据流出范围及适用授权。

**指标**（分别记录模型与数据切分，不预定虚构阈值）：
- 检测：每类 recall/precision、远小目标的漏检率、推理耗时；
- ReID：Top-1、Top-5、mAP（需正负标注与候选库）、误关联率、拒识/未知保留率；
- 属性：可见属性逐项准确率、unknown 比例、对遮挡缺失的误否定比例；
- 时空：明显不可能路径的拦截率、真实可行路径误排除率；
- 动态更新：Top-K 改善幅度、目标漂移率、人工撤销可用性；
- 性能：每模型 CPU/GPU 延迟、内存/显存峰值、每分钟可处理帧数。

**报告口径**：每次实验保存模型名、模型权重 SHA256、预处理输入尺寸、阈值、Prompt hash、图片 SHA256、标注版本、时间来源、成功/失败状态。初步验收以“可复现的正负例结果和可解释排名”为准，**不以模型相似度 > 某值作为自动确认身份**。

## 6. 分工、接口与不重复建设

```text
主工作台：用户指定调查目标 → 人工证据/待核查候选（无模型试验按钮）
         │
         ▼
左侧「模型测试」：输入参考 A + 搜索 B → 检测/Person ReID 排名
         │                                            │
         │                     后续车辆 ReID / 属性消融 / 时空测试
         ▼
参考图 / 已确认多视角 / 待核实候选隔离 / 版本回滚
         │
         ▼
同录像多帧补全 → 同时调度多台摄像头录像 → 候选轨迹还原
```

- `detectors.py` **仍只负责框检测**，不要将 embedding 当成 detection box 塞进已有 `/ai/image-models` 字段；ReID 通过**单独的实验适配层**暴露，与检测器共享推理资源纪律。
- `m4_vision.py` 继续负责人员/车辆提示词解析及原图 ROI 裁剪；正式结构化属性字段/持久化须单独版本化，不覆盖 M4a 人工观测。
- 取帧只走 [26](26_能力地图与复用契约.md) 唯一入口，不新造 seek / ffmpeg 轮子。
- 任何自动候选均应能展示“不确定”和失败，不得自动提升为“人工核实”。

## 9. 2026-11-01 真实 OSNet 权重安装与基线评测

### 9.1 权重与格式（关键坑）

| 项 | 值 |
| --- | --- |
| 模型 | OSNet x0.25（MSMT17 训练），ONNX |
| 来源 | HuggingFace `anriha/osnet_x0_25_msmt17`（MIT） |
| 落盘 | `backend/models/reid/osnet_x0_25_msmt17_b1.onnx`（0.87 MB，gitignore） |
| SHA-256 | `f3352b03dc6a188836af98ebadb1234b8b9083b3fa9bbd1077d1c559ab7374fa` |
| 输入 / 输出 | `[batch,3,256,128]` → `[batch,512]`（L2 归一化在引擎侧做） |
| CPU 耗时 | 单张 crop ≈ 8 ms；16 人一次请求 0.60 s |

原模型导出时把 batch 固定成 **16**，而 `ReidOnnxEngine` 逐 crop 送 **batch=1**，直接加载会在
`session.run` 处报形状不符。处理方式是把 ONNX 的输入/输出第 0 维改成动态 `batch`
（`onnx` 改图，不动权重），得到 `*_b1.onnx`。**换任何来源的 OSNet ONNX 都要先确认这条。**

配置（`.env`，不入库）：

```
M6_PERSON_REID_MODEL_PATH=models/reid/osnet_x0_25_msmt17_b1.onnx
M6_PERSON_REID_MODEL_SHA256=f3352b03dc6a188836af98ebadb1234b8b9083b3fa9bbd1077d1c559ab7374fa
```

```
  #5 sim=0.516 idx=16
```

说明链路与相似度量级正常（同 crop=1.0，不同人 0.5 上下），但这只是**一致性自检**，不代表跨视角识别力。

### 9.4 x1.0 权重的导出结果（未纳入基线）

官方 `osnet_x1_0_msmt17`（torchreid 权重，16.5 MB .pth）已用 `torchreid.models.build_model` +
`torch.onnx.export(dynamo=False)` 导出为 `osnet_x1_0_msmt17_b1.onnx`（7.3 MB，input `[batch,3,256,128]`

**但没有用它出分数**：同一台机器上 x1.0 单张 **581 ms**，x0.25 只要 **18 ms**（32 倍差距，

- **基准分数不等于现场效果**：监控画面的目标更小、更糊、遮挡更多；仓库里目前没有 `storage/videos` 录像，
  没能做“同一录像跨帧”的现场验证。

## 10. P1-A-3｜真实监控同录像跨帧验证（2026-11-01）

素材：`G:\测试数据\视频\29\1-LT-桂康路松山巷_20261023150000至20261023153030\…mp4`
（2560×1440、25 fps、30.5 min、HEVC，固定枪机俯视路口）。取 88–208 s 之间每 4 s 一帧，共 31 帧。

### 10.1 检测层先暴露了问题

D-FINE(`dfine-n`, conf 0.3) 在这 31 帧里产出 **419 个 person crop（≈13.5 个/帧）**，
但人工核对 t=88 s 那一帧的 15 个框：真人只有 5 个（两名骑手 + 粉衣女士 + 重复框），
其余是**停放的电动车、摩托车、墙上广告牌**被当成 person。

> 后果：ReID 的候选库被非人 crop 污染，排序噪声大。这直接决定「Top-5 有没有意义」，
> 与 §1.1「检测只负责发现候选」一致——检测精度不足时，ReID 再好也无法补救。

### 10.2 静态目标：跨 120 秒仍然稳定第一

目标：坐在电动车上的粉衣女士（crop 高约 90 px，位置几乎不动）。参考帧 t=88 s。
真值用「框中心 ±40 px」自动标注（她全程未移动），31 帧中 30 帧存在。

| 指标 | 结果 |
| --- | --- |
| Top-1 | **30 / 30** |
| Top-5 | **30 / 30** |
| 正样本相似度 | min 0.651 / p10 0.831 / mean **0.862** |
| 同帧最高负样本 | 0.542 – 0.685 |
| 时间跨度 | 88 s → 208 s（120 秒） |

即：**只要目标够大、衣着有辨识度、视角基本不变，x0.25 在真实画面上是能用的**，
正负样本之间有 0.15 左右的间隔。

### 10.3 移动/小目标：得分与噪声地板无法区分

目标：红盔骑手（前景，crop 高 139 px，约 2 秒内驶出画面）。

| 项 | 结果 |
| --- | --- |
| 跨帧最高相似度 | **0.650** |
| 人工核对 top-10 | 全是误检的摩托车/电动车，**无一命中** |
| 无目标地板（160 s 之后的 161 个 crop） | **0.642** |

结论：**0.65 这一档等于随机**。对小目标/快速移动目标，当前 x0.25 排序没有可用信息量；
如果按 0.75 设阈值，这类目标会被全部拒识——这比给出错误的第一名更诚实。

### 10.4 视角变化（短时间差）

t=86 s 与 t=86.5 s 两帧，白色短袖骑手：同一个人不同角度 **0.788**，
同帧另一名浅色上衣骑手 **0.647**，其余候选 ≤0.62。Top-1 正确，但只有 0.14 的间隔——
「两个人都穿浅色上衣」这种难负例已经接近可分边界。

### 10.5 结论

1. **能力边界清楚**：大而清（≥~90 px）+ 有辨识度衣着 → 可用；小而糊（≤~70 px）或快速移动 → 不可用。
2. **必须引入拒识**：建议初始阈值 0.72–0.75，低于阈值返回「没有足够证据表明画面中存在该目标」，
   禁止永远拿第一名当匹配成功。
3. **检测质量是瓶颈**：先解决 person 误检（提高阈值、按长宽比/最小尺寸过滤、同目标去重），
   再谈 ReID 排序——否则错误候选会先占满 Top-5。
4. 本轮仍是**单帧对单帧**，未接入连续帧动态更新（P2）与跨摄像头约束（P3）。


## 11. P1-A-4｜检测质量与拒识验证（2026-11-01，同一段录像、同一 x0.25 权重）

### 11.1 先纠正上一轮的实验条件错误

§10.3 的「移动目标没有命中」是**取样间隔造成的假失败**：红盔骑手约 2 秒驶出画面，
而当时每 4 秒抽一帧，搜索帧里根本没有他。改用 **0.25 秒间隔**重做（85.5 s 起 4 秒、16 帧、230 个 crop）：

| 排序 | 帧（相对时间） | 相似度 | 人工核对 |
| --- | --- | --- | --- |
| #2 | t+0.50 s | **0.952** | 同一名白短袖骑手（侧后方） |
| #3 | t+0.25 s | **0.944** | 同一人 |
| #4 | t+0.75 s | **0.912** | 同一人 |
| #5 | t+1.00 s | **0.798** | 同一人（更近、更大） |
| #6 | t+1.25 s | **0.721** | 同一人（面部特写） |
| #7 | t+1.25 s | 0.721 | 同一人的重复框 |
| #8 | — | 0.699 | **第一个非目标**（另一名白衣骑手） |

结论：**只要搜索帧里确实有目标，x0.25 能把移动骑手连续排在第一**，相似度随距离/姿态从 0.95 衰减到 0.72。
上一轮「移动目标不可用」的结论作废，改为「稀疏抽帧会制造假阴性」。

### 11.2 检测候选质量（5 帧人工标注，70 个 person 框）

标注文件：`backend/scripts/p1a4_detection_labels.json`（real / dup / 其余按误检计）。真实人体框 14 个。

**只调置信度**（precision = TP / 全部保留框）：

| conf | 保留 | TP | FP | 重复 | precision | 相对召回 |
| --- | --- | --- | --- | --- | --- | --- |
| 0.30 | 70 | 14 | 49 | 7 | 0.20 | 14/14 |
| 0.40 | 26 | 11 | 11 | 4 | 0.42 | 11/14 |
| 0.50 | 17 | 10 | 7 | 0 | 0.59 | 10/14 |
| 0.60 | 5 | 3 | 2 | 0 | 0.60 | 3/14 |

**单变量过滤**（conf≥0.30）：

| 过滤 | TP | FP | 重复 | precision |
| --- | --- | --- | --- | --- |
| 最小高度 h≥80 px | 11 | 11 | 4 | 0.42 |
| 长宽比 0.25≤w/h≤0.75 | 8 | 13 | 5 | 0.31 |
| 同帧去重 IoU≥0.5 | 14 | 42 | 3 | 0.24 |

**组合**（推荐）：conf≥0.40 + h≥70 px + 同帧去重 → **TP 11 / FP 9 / 重复 0，precision 0.55，相对召回 79%**。

> 长宽比过滤单独用会把骑手一起滤掉（14 个真人里丢 6 个），与「骑车人框偏宽/不完整」的预判一致，
> **不建议作为主过滤条件**；尺寸阈值按画面高度换算更稳（70/1440 ≈ 4.9% 画面高）。

### 11.3 拒识阈值（目标存在 / 不存在两组）

存在组：骑手 5 帧（0.72–0.95）+ 粉衣女士 30 帧（逐帧最高 0.808–0.93）。
不存在组：骑手离场后 13 帧（逐帧最高 0.681）。

| 阈值 | 骑手命中 | 粉衣命中 | 误接受（不存在却给分） |
| --- | --- | --- | --- |
| 0.65 | 5/5 | 30/30 | 2/13 |
| **0.70** | **5/5** | **30/30** | **0/13** |
| **0.72** | **5/5** | **30/30** | **0/13** |
| 0.75 | 4/5 | 30/30 | 0/13 |
| 0.80 | 3/5 | 30/30 | 0/13 |
| 0.85 | 3/5 | 26/30 | 0/13 |

**0.70–0.72 是这组数据上的分界点**：零误接受，且骑手/静态目标都还能进候选。
0.75 以上开始漏掉刚进入画面、尺寸还在变化的目标。

三态输出（不是身份确认，只是候选可信度）：

| 状态 | 条件 | 前端措辞 |
| --- | --- | --- |
| 候选值得核查 | 最高分 ≥ 0.72 且与次高分有明显间隔 | 列出候选，标注相似度与来源帧 |
| 证据不足 | 最高分 < 0.72，或分数接近、画质差、遮挡明显 | 「没有足够证据表明当前画面存在该目标」 |
| 未检测到可用人员 | 检测层 0 个合格 person 框 | 与「证据不足」分开呈现，提示换画面或调阈值 |

### 11.4 引擎异常不再被当成「没有人」

`dfine_engine` / `onnx_engine` / `openvino_engine` / `pytorch_engine` / `yolo_pytorch_engine`
原来在 `detect()` 里 `except Exception: return []`，导致「推理失败」和「图中没有目标」不可区分。
现改为抛 `EngineInferenceError`（`app/engines/base.py`），由 `detectors._detect_locked` 转成
`DetectorError("detector_inference_failed:<id>")`；`yolo_postprocess` 的解码失败同样改为抛出。

副作用：调用方看到的是 503 类错误码，而不是「候选 0 个」——这正是引入拒识前必须分开的两件事。
测试：`test_detectors_registry.py` 新增 `test_engine_failure_is_not_reported_as_no_objects` 与
`test_engine_returning_empty_is_not_a_failure`。

### 11.5 本轮的三个问题与结论

| 问题 | 结论 |
| --- | --- |
| 能否减少非人误检而不牺牲骑手召回 | 能：conf 0.40 + h≥70 + 去重，precision 0.20 → 0.55，相对召回 79%；**不要用长宽比过滤** |
| 搜索帧有目标时 x0.25 能否排前 | 能：连续 5 帧 Top-1，0.95 → 0.72，首个非目标 0.699 |
| 目标不存在时能否说「证据不足」 | 能：阈值 0.70–0.72 时 13 帧误接受为 0，同时不误杀已确认的目标帧 |

限制：5 帧检测标注、13 帧缺席样本、一台相机、两个目标——数字是指示性的，不是统计结论；
阈值仍需在更多相机与画质条件下复核后才能写成产品规则。


## 12. P1-A-5｜两级候选池与三态拒识接入模型测试页（2026-11-01）

### 12.1 后端

`m6_person_reid.py` 新增：

| 函数 | 作用 |
| --- | --- |
| `split_candidate_pool(image_size, candidates, high_conf, min_height_px, dedupe_iou)` | 只取 person → 同帧去重（IoU 贪心，保置信度高者）→ 按「置信度」和「最小高度」分高质量/备用两池 |
| `_decide(pool, ranking, threshold)` | 三态判定：`candidate_for_review` / `insufficient_evidence` / `no_person_candidate` |

- 备用池**不丢弃**：低置信度、过小的框仍会算相似度，放在 `backup` 里返回，供人工核查与相邻帧复核。

- `margin` 只在去重后的不同目标之间计算，避免同一目标的重复框制造「差距为 0」的假象。

## 13. P1-A-6｜第二机位（菜市入口）密集场景对照（2026-11-02）

### 13.1 素材与做法

- 源录像：`G:\测试数据\视频\29\3-DX-桂康菜市入口-球_20261023145956至20261023153027.mp4`，1920×1080、25 fps、30.5 min、视角固定。
- 流程：0.5 fps 抽 916 帧 → D-FINE N（conf 0.30）→ person 裁剪 → OSNet x0.25 提特征，共 **8760 个裁剪**。
- 不做人工标框：静态摊主用 IoU 跟踪（阈值 0.25）取逐帧对应框；行走顾客用同样方式取到 12 帧轨迹。
- 排名前先做**同帧去重**（IoU 0.5，保置信度高者），与 P1-A-5 上线逻辑一致。
- 缺席集：行走顾客离场 10 分钟后（≥600 s）的 616 帧，取逐帧最高分。

### 13.2 场景统计

| 指标 | 数值 |
| --- | --- |
| 每帧人数 | 中位数 **10**，p90 13，最多 20 |
| 每帧 ≥5 人的比例 | **96%** |
| 人体高度 | 中位数 91 px；≥120 px 35%，≥150 px 11% |

与松山巷路口（每帧 13.5 人但 20% 达 80 px）相比，这里是「人多且更大」的密集场景。

### 13.3 目标排名

**静态摊主（跟踪 90 帧，跨全片）**

| 目标 | Top-1 | Top-5 | 自身分数 min / p10 / 中位 |
| --- | --- | --- | --- |
| 摊主 A（125 px） | 83/90 = **92%** | 90/90 = **100%** | 0.676 / 0.752 / 0.893 |
| 摊主 B（131 px） | 71/90 = **79%** | 90/90 = **100%** | 0.734 / 0.831 / 0.877 |

> **勘误（2026-11-02，T0 人工逐帧核验发现）**：上表「摊主 A / 摊主 B」用的两个框，逐帧核对后实为
> **停放电动车、遮阳棚与座垫的静态误检**，不是人。它们作为"同一静止区域跨 30 分钟的向量稳定性"
> 仍然成立（中位 0.88–0.89），但**不能当成人员 ReID 的 Top-1/Top-5 证据**，这两个数字不再作为 P1-A-6 的人员结论引用。
> 同批数据里的人员结论只保留**行走顾客**（Top-1 10/12、Top-5 12/12）。
>
> 这也暴露了一个此前没测的项：该机位 person 检测里**静态误检占比很高**——贪心 IoU 建出的 2349 条轨迹中，
> 长轨迹多数是物体（电动车、遮阳棚、货箱），真实行人轨迹反而短。检测精度需在 T0.2 单列统计。

> 未做同帧去重时两者分别为 76% 和 48%——同一目标被检出多个框会把自己的排名挤下去。
> **Top-5 恒为 100%**，这是去重前后都不变的事实：目标一直在候选里，只是"第几"受重复框影响。

**行走顾客（72 px，22 秒共 12 帧）**

| Top-1 | Top-5 | 自身分数中位 | 最弱 |
| --- | --- | --- | --- |
| 10/12 = **83%** | 12/12 = **100%** | 0.812 | 0.451（192 s，被路人挡住且框不完整） |

### 13.4 密集场景把「地板」抬高了

| 机位 | 目标存在 | 目标不存在（逐帧最高） | 间隔 |
| --- | --- | --- | --- |
| 松山巷路口（稀疏，13 帧） | 0.86 | 0.642 | 0.22 |
| **菜市入口（密集，616 帧）** | 0.81 | **0.726**（p99 0.699） | **0.09** |

阈值对照（行走顾客，缺席 616 帧）：

> 「目标保留」指**目标本人那个框**的相似度达到阈值，不是「该帧存在某个高分候选」。

| 阈值 | 目标保留 | 缺席误收 |
| --- | --- | --- |
| 0.65 | 11/12 | 22/616 |
| 0.70 | 10/12 | 7/616 |
| **0.72** | **9/12** | **1/616** |
| 0.75 | 7/12 | 0/616 |
| 0.78 | 7/12 | 0/616 |
| 0.80 | 7/12 | 0/616 |

**0.72 在这个机位会误收 1 次**；要零误收得抬到 0.75，但代价是 12 帧里只剩 7 帧。

> 静态摊主不参与这张表：她整段都在画面里，跟踪断开的帧其实是遮挡或框漂移，
> 那些帧的「最高分」仍是她自己，拿来做缺席集会把地板虚高到 0.95。
> 计算脚本 `backend/scripts/reid_dense_scene_eval.py` 会把这类情况如实打印成"缺席帧"，需人工判断。

### 13.5 为什么单阈值不能跨机位复用

遮挡/截断把目标分数压到 0.69–0.73，而画面另一端另一个白衣骑手能拿到 0.73——**两个分布重叠**。
任何单一阈值都只能二选一：漏掉被摊棚遮挡的本人，或者收下一个相似穿着的路人。

这也说明 P1-A-5 的做法方向是对的：**分数只是输入，还要看 margin、看质量档（备用池）、看是否多帧连续出现**。
把 0.72 写死成业务规则，在第二个机位上就已经不成立。

### 13.6 结论与限制

- 密集场景地板从 0.64 抬到 0.73；阈值必须按机位/场景标定，建议默认区间：稀疏 0.70–0.72、密集 0.75–0.78。
- 同帧去重对 Top-1 影响巨大（48%→79%、76%→92%），进一步支持 P1-A-5 把去重放在排序之前。
- **限制**：单机位、单时段；行走样本只有 12 帧；静态目标的 Top-1 仍受同帧重复检测影响（已去重，但跟踪框可能与最优框不完全一致）；缺席集只覆盖「完全离场」，未覆盖「仍在画面但被完全遮挡」。
- 因此本节数字仍是**指示性**的：它证明了"阈值随场景变化"，而不是给出某个机位的最终阈值。


### 13.7 统计口径修正与人工核验（2026-11-02）

**修正一：目标分数被算成了该帧最高分。**

初版 `reid_dense_scene_eval.py` 记录的是 `scored[0][0]`（该帧所有候选的最高分），
而它不一定属于目标本人。修正后分别记录：

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `target_similarity` | 目标跟踪框所在候选的相似度 | **阈值命中只看它** |
| `best_similarity` | 该帧全部候选的最高分 | 只用来判断该帧是否存在高分候选 |

修正后的差距（同一份 gallery）：

| 目标 | 修正前 p10（误用最高分） | 修正后 p10（目标本人） |
| --- | --- | --- |
| 摊主 A | 0.858 | **0.752** |
| 摊主 B | 0.851 | **0.831** |
| 行走顾客 | — | 0.687（min 0.451） |

阈值表的命中数在本批数据上没有变化（目标多数帧本就是第一名），
但**只要出现「别人 0.78、本人 0.69」的帧，旧口径就会把它记成保留**——
这类帧在行走目标上确实存在（见下），所以后续所有阈值结论都改用 `target_similarity`。

**修正二：gallery 缺少 `conf` 字段。**

`reid_cross_frame_eval.py` 原来写出的 `gallery.json` 没有 `conf`，
而密集场景评测的同帧去重需要按置信度排序。现在：

- `reid_cross_frame_eval.py` 在每条记录里写入 `conf`；
- `reid_dense_scene_eval.py` 在缺少 `conf` 时退化为「按原顺序保留」，并**打印提示**，
  不静默改变排序依据。两个脚本现在可以互相独立复现。

**人工核验：12 帧行走轨迹逐帧看过，没有换人。**

| 时间 | 排名 | 目标分 | 人工核对 |
| --- | --- | --- | --- |
| 192 s | 2 | 0.451 | 本人，但被路人挡住、框不完整 |
| 194–202 s | 1 | 0.744 / 0.825 / 1.000 / 0.874 / 0.815 | 本人 |
| 204 s | 2 | 0.730 | 本人，但被一个 29×42 的头部碎片框（0.742）挤到第 2 |
| 206–214 s | 1 | 0.815 / 0.823 / 0.809 / 0.706 / 0.685 | 本人，越走越近、框逐渐被画面边缘截断 |

**这两次第 2 名都来自「同一个人的碎片框」，不是别人。** 例如 204 s：

```
0.742  #12  box=[609,291,638,333]  29×42   头肩碎片，conf 0.33
0.730  #1   box=[611,294,649,381]  38×87   完整身体（跟踪真值），conf 0.59
```

两框 IoU 只有 0.30，同帧去重（IoU 0.5）不会把它们合并，于是碎片把本人挤到第二。
这正是下一步要做**轨迹级合并**的直接证据：去重只能处理"同一目标被重复框出"，
处理不了"同一目标被框成不同部位"。
