# 添加要素：截图定位点、可拖时间框、录像回填路径与特征栏改版（规划）

> 依据：用户 2026-11-07 需求（m00939）。B8-S 空间标定按 [64](64_B8-S_V1.2_阶段归档.md) 已归档、分支已收；
> 本规划**复用其代码与术语，不重开 B8-S 分支**，新工作落在 main。
> 定位：把「添加要素」从“只在内存里加一条记录”升级为“截图即定位、定位即入时间轴、录像自动补轨迹”。

## 一、结论摘要

| 用户要求 | 实现方式 | 本轮是否做 |
| --- | --- | --- |
| 截图里的摄像头名称 → 地图定位点 | Map 台账解析 camera_uuid → 标定/L2 投影，失败退实验射线投影，再失败退区域占位 | 做 |
| 时间轴出现对应时间卡 | 新增要素卡，时间取截图角标，`observedAtSource='screenshot_osd'` | 做 |
| 定位点连细线到一个框，框内显示截图时间，框可拖 | 点是地理真值，框是标签；拖动只改 `label_offset` | 做 |
| 图层开关控制时间框显隐 | `layers.targetTimeBoxes`（默认开）+ 图层面板一行 | 做 |
| 点/框 选中右侧时间轴卡片 | 复用唯一选中真源 `actions.selectTimelineCard` | 做 |
| 完整截图：后台读这段录像，补特征、补空间路径 | 找覆盖该时刻的 clip → 复用 tracking-run → segments 回填 | 做（先出路径，特征建议第二批） |
| 有路径后不再显示点，显示路径；框显示起止时间 | 路径折线 + 起止两行标签；轨迹点仍可点 | 做 |
| 局部截图：不定位，只在特征栏加特征 | 判定为局部时跳过锚点/卡片/后台，只写目标组 | 做 |
| 特征栏改版：左大图（目标 + 关联），右可编辑特征 | 重写特征面板，左图右表 | 做 |
| 自动空间标定（无人工接地点） | B8-S 已归档，本轮不做 | 不做 |

## 二、现状核对（2026-11-07 代码实测）

已有、可直接复用：

- **截图 → 观测**：`mainApi.uploadMedia` → `POST /api/v1/media/{id}/observations`（`m4_api.py:85`），落 `TargetObservation.analysis_json`（含 `bbox_pixels`/`bbox_normalized`）、`source_context{time_candidate,time_verified:false,camera_verified:false}`。
- **截图 → 时间/相机名**：`POST /api/v1/media/{id}/inspect`（`main.py:289`，module `media_inspector_m1d`）→ `InspectionReport`；前端 `recognize()`（`AddElementModal.vue:528`）已把候选填进 `date/timeLabel/cameraName`，目录命中写 `confirmedCamera`。
- **要素落库**：`POST/PATCH /api/v1/cases/{case}/target-groups`（`target_group_api.py:26,54`）→ `target_element_groups/objects/relations/attributes`；`GET` 列表已存在（`:32`）。
- **L2 投影**：`POST /api/v1/cases/{case}/observations/{obs}/ground-projection`（`m6_l2_api.py:29`），要 `ground_contact_pixel` + `calibration_id`（或内联 calibration），落 `target_spatial_observations`。
- **实验投影**：`POST /api/v1/experimental-projection`（`m6_experimental_api.py:58`）、`POST /api/v1/track-spatial`（`m6_track_spatial_api.py:38`），`persisted=false`。
- **录像**：`recording_clips(camera_uuid, camera_name, start_local, duration_seconds)`，`GET /api/v1/recordings/clips?case_id=`；帧/关键帧/代理播放已在 `m6_video.py`、`recording_api.py:310`。
- **追踪**：`POST /api/v1/cases/{case}/tracking-runs`（`m6_run_api.py:136`）+ worker（`m6_run_worker.py`），anchor 带 clip 与绝对秒。
- **时间轴**：`GET .../timeline`（技术卡）与 `.../timeline-view`（主卡），前端唯一选中真源 `wb.selectedCardId`。

缺口（必须补）：

1. 要素**只在内存**（`workbench.ts:251` 注释），刷新即丢；锚点与轨迹没有承载处。
2. `TargetElementObject` 无 `camera_uuid`/时间/像素框；`target_spatial_observations.observation_id` 是 NOT NULL FK 到观测，**空间点挂不到要素组**（`models.py:376`）。
3. 只有 `read_ground_calibration(dsn, calibration_id)`；**没有「相机 → 已审核标定」反查**（`map_db_spatial.py:262`）。
4. 时间轴不认识要素：`timeline_projection` 数据源只有 `TargetObservation` 出发（`:431-448`）。
5. 现存 bug：`timeline_projection._point` 读 `ground_point["lat"]/["lon"]`，而 L2 写 `{"x","y","crs"}` → 所有空间卡恒 `position=None`、`degradeReason="no_ground_point"`（`:78-79`、`:229-231`）。
6. 现存 bug：`m6_l2_api.py:33` `fail(404,'case_not_found')` 少第三个参数，实际 500。
7. 地图无可拖 marker 先例（全仓 `draggable` 0 命中），且 `render()` 是全量清空重绘（`WorkspaceMap.vue:670-672`），拖动会被打断。

## 三、冻结的设计基线

| # | 设计项 | 决定 | 理由 |
| --- | --- | --- | --- |
| 1 | 完整截图判定 | 有 OSD 时间（或文件名兜底时间）**且** 相机能唯一落到 Map 镜头 | 两者缺一就不是“有时间和地点” |
| 2 | 半完整处理 | 有时间无镜头：出时间卡、不定位；有镜头无时间：出定位点、框写“时间未知”、不跑录像 | 只做能做的，界面明说缺哪一半 |
| 3 | 局部截图 | 无线索或名称无法唯一匹配：不建锚点、不建卡、不跑后台，只写目标组 | 用户明确要求 |
| 4 | 定位分级 | L2 标定点 > L1 实验点 > L0 区域占位；等级不同、颜色不同、文案不同 | 不自降为正式 L2，也不因缺标定就完全不给点 |
| 5 | 接地点 | 默认 bbox 底边中点，允许在截图上点选校正；未校正标 `contact_source='bbox_bottom_center'` | B8-S 禁止拿框中心当接地点，底边中点同样要标未核验 |
| 6 | 时间框性质 | 框是**标签**不是地理图形；拖动只改 `label_offset`，`ground_point` 不动 | 否则拖一下就把“估计位置”变成“用户指定位置”，是编造 |
| 7 | 时间语义 | 时间来自角标 OCR，`capture_verified=false`、`timeQuality='osd_unverified'`；卡片不得称“精确时刻” | 与 M1d/B7 口径一致 |
| 8 | 轨迹回填窗口 | `[t0-30s, min(t0+90s, clip_end)]`；若目标在窗口末尾仍在视野内，按 30s 步长**自动追加**，直到目标离开视野 / 片段结束 / 累计 15 分钟上限；窗口内取不到连续轨迹就保留点 | 用户 2026-11-07 定：前 30 秒后 90 秒，持续可见则自动延长 |
| 9 | 路径与点 | 有 ≥2 个有效地面点才换路径；路径保留起止框；点的点击仍可用 | 单点不给方向（B8-S 结论） |
| 10 | 图层 | 新增 `targetTimeBoxes`（默认开）、`elementTrace`（默认开） | 用户要求“图层中可选择是否显示目标时间框” |

## 五、接口

### 5.1 新增

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/v1/cases/{case}/elements/{group_id}/anchor` | 建锚点：解析镜头→投影→写行；完整截图且有录像则建追踪任务 |
| `GET` | `/api/v1/cases/{case}/elements/anchors` | 列表（含 trace 摘要） |
| `PATCH` | `/api/v1/cases/{case}/elements/anchors/{anchor_id}` | 只改 `label_offset`（拖动）与 `pixel_xy`（人工校正接地点，需重算投影） |
| `GET` | `/api/v1/cases/{case}/elements/{group_id}/trace` | `{status, runId, segments[], window}` |
| `GET` | `/api/v1/cases/{case}/elements` | 要素读回（group + objects + attributes + anchor + trace 摘要），供刷新后重建 |

`POST anchor` 请求体：

```json
{ "object_id": "P1", "media_id": "...", "camera_uuid": "…|null", "camera_name": "…",
  "capture_local": "2026-10-23T15:00:05", "capture_source": "osd",
  "pixel_xy": [x, y], "frame_size": [2560, 1440], "base": "full|crop",
  "trace": true }
```

服务端顺序：`base=crop` → 直接返回 `skipped`（不写行）→ 解析镜头（uuid 优先，否则按名称精确唯一匹配台账）→ 查标定 → 投影（L2/L1/L0）→ 写行 → 若 `trace` 且 `camera_uuid` 且时间有效 → 找 clip、建 run、`trace_status=queued`。

### 5.2 修复

- `timeline_projection._point`：接受 `{lat,lon}` 与 `{x,y,crs}` 两种（`crs=="EPSG:4326"` 时 `lon=x, lat=y`），否则不改写、标 `degrade_reason`。
- `m6_l2_api.py:33` 补 `fail()` 第三参。
- 新增 `map_db_spatial.read_ground_calibration_for_camera(dsn, camera_uuid)`：同 SQL 加 `AND camera_uuid=%s` + `ORDER BY created_at DESC LIMIT 1`，仍只读、仍只认 `review_status='approved'`。

### 5.3 时间轴接入

`timeline_projection` 增加两类卡（数据源加 `target_element_anchors`）：

- `element_anchor`：`cardId=element:{anchor_id}`、`observedAt=capture_local`、`place=camera_label`、`position=ground_point`、`spatialQuality=projection_quality`、`evidence.mediaId`。
- `element_trace`：有路径时替换锚点卡的 `subtitle`（`15:00:05–15:01:12 起止`），不额外增加一张卡，避免列表膨胀。

`timeline-view` 的 `counts` 增加 `element` 一项；主视图把要素卡排在区域卡之前（同一时间序）。

### 5.4 坐标契约

统一出口 **经纬度**：`ground_point={lat,lon,crs:'EPSG:4326'}`。L2 原响应是 `{x,y,crs}`，服务端落库前转换；`crs` 不是 EPSG:4326 时**不猜**，降级 L0 并记 `degrade_reason='world_crs_not_wgs84'`。

## 九、不做的事 / 风险

- 不做自动空间标定（`b8_auto_calibration_enabled` 保持关）；不把 L1 升级成 L2；不声称米级精度。
- 不用检测框中心或类别先验当接地点；没有像素证据就不给点。
- 不做跨镜头 ReID；不做时间轴横向缩放轴（本轮纵向列表 + 地图时间框）。
- 不移动/重命名/裁剪录像文件；回填只读。
- 风险：`render()` 全量重绘与拖动冲突（见六）；`capture_local` 依赖 OSD 质量，角标读错会写错时间——因此 `capture_verified` 恒 false，界面标“待核实”。

## 十、已确认（2026-11-07）

## 十二、接线缺陷修复计划（2026-11-07 用户实测反馈）

用户实测：页面与模块都在，但「添加要素」之后 ①不进时间轴卡片 ②地图上没有定位点 ③特征栏里的要素/特征删不掉。

### 12.1 诊断结论（已定位，非猜测）

| 现象 | 根因 | 证据 |
| --- | --- | --- |
| ① 无时间轴卡片 | `AddElementModal.save()` 里 `payload` 在第 1008 行构造时 `targetGroupId: groupId` 还是 `null`（目标组在第 1051 行才创建、1065 行才赋值给局部变量 `groupId`），`payload` 不会跟着变 → `saveElement` 不写 `elementGroupIds`，`syncAnchor` 第 1225 行 `if (!groupId …) return` 直接返回 | `saveElement` 只在 `payload.targetGroupId` 存在时记录映射（store:1834） |
| ② 无地图定位点 | 同上：没有 groupId 就没有 `POST .../anchor`，`anchorByElement` 永远空，`WorkspaceMap` 只能落到「待定位区域」圈 | DB `select count(*) from target_element_anchors` = **1**，且那一行是我 02:24 的接口冒烟，不是 UI 产生 |
| ③ 删不掉 | 前端与后端都没有删除能力：`TargetFeatureBar.vue` 零删除入口；`target_group_api.py` 只有 POST/GET/PATCH，没有 DELETE；单条特征也没接「删一项」的 PATCH | `Select-String '删除|delete' TargetFeatureBar.vue` 无命中 |

附带发现的同类问题（同一批修）：
- `updateElement()`（编辑已有要素）不重算锚点：改了时间/镜头后地图仍用旧位置。
- `loadElements()` 用 `base = anchor ? "full" : "crop"` 反推截图类型，导致「完整截图但定位失败」的要素刷新后被当成局部截图，卡片与定位一起消失（把①的失败放大成数据丢失）。
- 时间轴卡完全由 `anchorByElement` 驱动，定位一失败卡片就没了；产品要求是「完整截图 → 有卡」，卡与点应解耦。

### 12.2 P0 最小修复（1 处赋值，先让主链路通）

### 12.4 P2 删除能力（三层，都要）

1. **后端 `DELETE /api/v1/cases/{case}/target-groups/{group_id}`**

   - 媒体资产、截图、录像一律不动（只读证据）。
2. **前端 store `actions.deleteElement(elementId)`**：`window.confirm` 二次确认 → 调接口 → 本地清 `elementList` / `featureList` / `observationList` / `anchorByElement` / `traceByElement` / `elementGroupIds` → 自动选中下一个要素（没有了就 `emptyMode = true`）→ toast。
3. **特征栏入口**：

   - 关联对象行「移除此关联对象」：PATCH `objects` 去掉 `A1`、`relations` 置空。
- 验收：删除后刷新页面不再出现；`target_element_anchors` 对应行随组消失；特征删除后 revision +1 且修订历史可查。

### 12.7 时间轴卡片统一（2026-11-07 收尾）

用户反馈「时间轴卡片搞错了，应该用图中的卡片：①已经确认目标的 ②正在核查待确定的；删掉其他类型的时间轴卡片」。原因是 P1 给添加要素另起了一套 `.tm-element-card` 卡片（独立分区「添加要素 · 定位时间卡」），与主视图已有的卡样式并存，看起来像第三种卡。

- 删除整套自定义卡片：模板 `tm-elements` 分区、`.tm-elements*` / `.tm-element-*` 样式、`focusElementCard()`。
- `elementCards` 改为直接产出 `TimelineViewCard`，并进同一个 `allViewCards` 列表（与主视图卡一起按时间排序、一起走筛选计数）：
  - 有锚点（定位成功）→ `kind: "confirmed_track"`：「已确认目标」卡（绿点、无徽标、右侧放这张截图本身）。
  - 无锚点 → `kind: "region_investigation"`：蓝点 + 徽标「待确定」，副标题写「截图里没读到可匹配的镜头，位置待人工指定」。
- 卡片操作复用原有按钮：`查看详情` 对要素卡 = 选中该要素（右侧特征栏 + 地图时间框同步，要素没有技术卡可展开）；`定位` = `selectAnchor(null)` 后再选中，配合 `WorkspaceMap` 新增的 `watch(() => wb.selectedAnchorId)` 把地图移到定位点（zoom ≥ 17），重复点也重新居中。
- 主视图空态与筛选放宽：有要素卡时即使 `timelineView` 为空也照常渲染列表（此前会被「该目标还没有可用于主视图的研判记录」挡住）。
- 结果：时间轴只剩两种卡（已确认 / 区域排查·待确定），添加要素不再引入第三种卡片类型。`npm run build` 通过（127 modules）。

### 12.11 朝向取 Map 绘制值 + 定位点自动重算（2026-11-08）

用户截图反馈「空间标定的点怎么跑到摄像头后面去了，真实位置在红圈位置才对」。定位到两处：

### 12.16 验收指标模块与真值集（2026-11-08，长目标第 5 批）

计划文档 §6.2 列了 10 项验收指标，§6.1 又明确「视觉合理性、轨迹是否穿路、曲线是否平滑都不能当真实地理精度」。本批先把**能自动算、且不会造假**的那几项落成模块，其余保持"未冻结"。

**新增文件**

- `backend/app/m6_projection_metrics.py`：纯函数模块，不碰数据库、不发请求，输入是 `track-segments` 的响应体（可选真值集）。
- `backend/scripts/b8_projection_metrics.py`：命令行取数 + 写报告。
- `backend/tests/test_projection_metrics.py`：14 条单测（无真值 / 有真值 / 全降级 / 误发布 / 真值集校验）。
- `backend/data/truth/pilot_camera_truth.example.json`：真值集模板（`dataset_id: template-not-for-accuracy-claims`）。
- `backend/data/metrics/projection_<run8>.json`：真实 run 的报告产物。

**能自动出的指标**

| 指标 | 口径 | 出处 |
| --- | --- | --- |
| 自动投影覆盖率 | `experimental` / `total`（点级） | `overall.points` + `overall.rates` |
| 降级分布 | `degrade_reasons` 直方图 + 近/中/远分桶 | `overall.degrade_reasons`、`overall.buckets` |
| 不确定半径 | `median` / `p90` / `max`（按投影时的参数扰动半径） | `overall.uncertainty_radius_m` |
| 误发布率 | `spatial_level ∈ {L2, L3}` 的点数 / 总数，**必须为 0** | `gate.mis_published` / `gate.mis_publish_rate` |
| 真值位置误差 | 仅在提供真值集时计算：`median` / `p90` / `max`，可按 `range_class` 分组 | `truth.error_m`、`truth.by_range_class` |
| 误差区域覆盖率 | 误差是否落在投影时声明的不确定半径内 | `truth.declared_region` |

**故意不出的指标**

- `thresholds` 字段恒为 `null`。§6.2 的门槛要在评测前冻结，现在写死一个 2 m 就等于替业务承诺精度，所以模块只报数、不判合格。
- 不报「自动地理配准成功率」以外的标定成功率：当前 `cameras_ground_calibration` 仍是 0 行，正式 L2 一条都没有，算出来只会是 0% 或 100% 的假象。
- 不报断线正确性 / 时间轴一致性 / 时钟正确性：需要人工逐对核对，本批不假装自动化。

**真值集格式（`load_truth`）**

```json

  "camera_uuid": "345f9636-0dff-4fb5-87e9-01d5f1cb9e1d",
  "collected_at": "2026-11-08",
  "points": [
    { "id": "T1", "lon": 110.21138, "lat": 25.25662, "at": "2026-10-23T15:00:05",
      "source": "surveyed", "range_class": "near" }

}
```

- `source` 只接受 `surveyed` / `gnss_walk` / `map_control_point` / `manual_control_point`；`ray_projection` / `auto_projection` / `self_estimate` / `derived` 会被直接拒绝（`truth_source_is_algorithm_output`）——**算法输出不能当真值**，否则指标自证清白。
- 缺 `id` / 缺坐标 / 重复 `id` / `points` 为空都有独立错误码，脚本以非零退出。

**诚实边界：`time_checked`**

`track-segments` 里的 `t` 是**片段内**秒数（`Decimal`，如 `0.2`），`evidence.day_seconds` 同为片段偏移，不是当天时刻。所以真值点的 `at` 只有在投影点时间**本身是字符串时刻**时才参与时间容差过滤；否则按空间最近匹配并标 `time_checked: false`，报告里能一眼看出"这次匹配没校验时刻"。

对应地，未匹配分三种原因：`no_time_match`（有候选但时刻对不上）、`no_projected_point`（没有可配对坐标）、`too_far`（最近点超出 `max_distance_m`，默认 100 m），都带 `nearest_m` 便于排查。

### 12.17 逐帧样本保留策略与镜头参数缺口台账（2026-11-08，长目标收尾）

长目标 5 批做完后还剩两件"不做就会烂在库里"的事：`track_samples` 会一直长、13 台镜头永远投不出射线。本节只解决这两件，且都不靠猜。

**一、`track_samples` 是可重算的中间量，不是证据**

逐帧样本只服务一件事：读取轨迹时按**当前** Map 参数现算地面坐标（表里刻意不存 lat/lon）。因此它可以被清理，而证据链在 `tracking_runs` / `tracking_candidates` / `tracking_windows` 与关键帧上，那些一律不动。

保留规则（`backend/app/m6_track_sample_retention.py`）：

| 项 | 取值 | 理由 |
| --- | --- | --- |
| 粒度 | 每案件保留最近 `keep_runs` 个追踪任务，默认 `20` | 排障主要看最近几次跑批；更早的样本即使留着也没人再读 |
| 清理对象 | 只删 `track_samples` | 删 run 会连带丢候选与审核事件，等于毁证据 |
| 默认行为 | `dry_run=True`，只报告 | 先看将删多少行再落库 |
| 禁止事项 | 不按天数过期、不在 worker 热路径里删 | 案件可能停摆数月，按天数会把"唯一一次真跑"删光；跑批中途删样本会让刚算出的轨迹读不到 |

接口：

- `plan(db, *, case_id=None, keep_runs=20) -> dict`：逐案件 `{case_id, kept_runs, dropped_runs, dropped_samples}` + `total_dropped_samples`，不写库。
- `prune(db, *, case_id=None, keep_runs=20, dry_run=True) -> dict`：`dry_run` 为真时等同 `plan` 并标 `applied: false`；否则按 run 批量 `delete(TrackSample)` 后 `commit`，返回 `deleted_samples`。
- `keep_runs < 1` 抛 `ValueError('keep_runs_must_be_positive')`——传 0 等于"清空所有案件样本"，必须显式拒绝而不是静默执行。

命令行（`backend/scripts/prune_track_samples.py`）：

```
python scripts/prune_track_samples.py                      # 只报告
python scripts/prune_track_samples.py --apply              # 每案件留最近 20 个任务
python scripts/prune_track_samples.py --keep-runs 5 --apply
python scripts/prune_track_samples.py --case <case_id> --apply
```

**二、13 台镜头缺 FOV：出缺口台账，不填默认值**

`GET /api/v1/spatial/cameras` 的真实快照（`spatial_revision=mapdb-spatial:21e18d1d9728e2bf`）显示：

- 31 台全部 `pose_quality=calibrated`、`bearing_source=map_camera`，方位角/俯角/安装高度**一台不缺**；
- `ray_projection_ready=true` 18 台，另外 **13 台只缺 `horizontal_fov_deg`**；
- 31 台 `fov_provenance` 全是 `map_model_geometry_not_verified_coverage`：地图上那三圈视域是**按模型几何推的**，不是实测覆盖（`status=modelled_unverified`），所以它不能反过来当 FOV 的来源。

追查过但确实没有的替代来源：`cameras_camera.horizontal_fov_deg` 同样为空；`cameras_registry.raw_properties` 只有资源管理器导出字段（`indexCode`/`decodeTag`/`channelType`/`geometry` 等），**没有 FOV、焦距或镜头型号**。既然没有真实来源，就不能用 60° 这种"典型值"补——补完投影看起来通了，误差会直接混进实验轨迹，而报告里又看不出来。

`backend/scripts/b8_camera_parameter_gaps.py` 因此只产出台账（默认写 `backend/data/metrics/camera_parameter_gaps.json`）：

`policy` 字段把结论写进报告本身：**缺参数不出射线，退化到镜头位置点（L0），等外场台账补录**。补录入口（批量标定/手填 FOV 的写接口）留作下一批，因为当前 13 台连"填什么"都还没有。（**后续变更**：水平 FOV 已由 §12.19 按业务默认 80° 补齐并标 `default_80`，只剩朝向/俯角/高度还阻塞。）

**验证**

单台自动标定藏在镜头卡第三页签里，31 台要点 31 次；而自动标定真正的用法是"先把参数齐全的都算一遍，再人工审几条"。本轮补一个批量入口，只做发起与结果查看，**不做一键通过**。

**入口与位置**

- 新弹窗 `frontend/src/components/modals/BatchCalibrationModal.vue`（`BaseModal`，宽版），在 `App.vue` 里与其它弹窗并列挂载。

**表格与统计**

- 逐台一行，四列：镜头（`cameraCode`，无参照帧时补一行「Map 侧无参照帧」）／参数（齐全 或 缺什么）／作业（未发起 / 提交中 / 排队中 / 运行中 / 已完成 / 失败 / 参数不齐）／候选（`N 条` 或 `—`）。

**状态回读**

- `loadKnownJobs()` 用**空 `camera_uuid`** 调 `/spatial/auto-calibration/jobs` 一次拿全量作业，按镜头取 `created_at` 最新一条归位；这样重开弹窗能看到以前发起过、已出候选的镜头，而不是从「未发起」重来。
- `loadCandidateCounts()` 只给已有作业的镜头数候选（`/candidates/{uuid}`），没有作业的镜头不多打一次接口。
- 存在 `queued|running` 作业时 5 秒轮询一次，跑完自动停；关弹窗或组件卸载即 `stopPoll()`（`onBeforeUnmount`）。

### 12.21 真值点拾取器（2026-11-08）

**为什么不能用摄像头坐标当真值**

户主问过一个很自然的问题：镜头坐标已经是准的，为什么还要另外取点？因为要检验的正是「像素 → 地面」这条链路，而**摄像头坐标与姿态本身就是这条链路的输入**——拿输入去验证输出，等于用 A 验证 A，链路整体错了它也照样"通过"。项目里有现成反例：§12.11 里 `cameras_camera.direction=168` 与 `cameras_registry.bearing_deg=355` 差 187°，若把摄像头坐标当真值，射线永远从原点出发，这个 187° 的朝向错误**根本发现不了**。

摄像头坐标能做的是另外两件事，都不声称精度：①坐标系体检——把视域楔形叠在卫星影像上看是否压在自己所在的道路上，可判断台账是否 GCJ-02 未纠偏（偏移 50–500 m 量级）；②相对一致性——两台镜头先后拍到的点落在同一段路、间距与镜头间距相符、步行速度合理。

**因此真值来自卫星影像控制点**（`source=map_control_point`）：在 GIS 视图上点住地物（路口标线、楼角、井盖），得到 WGS84 坐标；时刻 = 录像起点（OCR/文件名，`recordingClips` 的 `start_local` 最新一条）+ 目标压在该地物上的帧秒数。两者分开存，不把「时刻」与「坐标」混成一个数。

**后端（`backend/app/truth_dataset_api.py`，新）**

- `POST /api/v1/spatial/camera-truth/datasets?overwrite=`：写前先过 `m6_projection_metrics.load_truth()` 自检，保证「存下来的文件也一定能被指标脚本消费」。

### 12.22 底图缩放上限跟瓦片源走（2026-11-08）

户主问「地图层级是否可以再放大些」。原来三处（`mapTiles()`、`imageryTiles()`、`LiveGisMap` 的 `maxZoom:19`）都写死 19，z19 以上点「+」不动。先测瓦片本身能不能给：

| 层级 | OSM | Google 影像 | Esri 影像 |
| --- | --- | --- | --- |
| z19 | 200 image/png | 200 image/jpeg | 403（本机整段被拒） |
| z20 | **400 Bad Request** | 200 | 403 |
| z21 | 400 | 200 | 403 |

- 结论：OSM 的 19 级就是**瓦片服务上限**（不是我们限制），Google 影像能到 21；Esri 在本机不可用。
- 改法：`basemapTiles.ts` 的 `ImagerySource` 增加 `maxZoom`（Esri 19 / Google 21 / OSM 19），`imageryTiles()` 用它初始化；回退换源时同步 `layer.options.maxZoom` + `map.setMaxZoom()` 并把 `maxZoom` 带进 `basemapchange` 事件。
- `WorkspaceMap.vue` 新增 `applyBasemapMeta(layer)` 与 `onBasemapChange(event)`：初始化、`swapBasemap()`、回退换源三条路径都把地图上限设成当前瓦片源的上限，当前缩放超出时降到新上限。
- 实测（playwright CDP 连真实页面）：`地图` 底图 z16→**z19** 顶住；`卫星` 底图 z16→**z21**，12 块瓦片全 `leaflet-tile-loaded`，状态栏「影像 © Google」，控制台无报错。截图 `.tmp_map_zoom_max.png`。
- 未动：`真实 GIS 地图`（`LiveGisMap.vue`）仍是 OSM 底图 + 19 级上限——它画的是路网/建筑矢量，换影像底图属于样式改动，另有需求再做。
