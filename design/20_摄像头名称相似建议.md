# 摄像头名称相似建议（2026-10-28）

> 解决的问题：OCR 从角标里读出的摄像头名称经常错一两个字（`0`↔`O`、`1`↔`l`、少一笔、多一个空格），
> 精确匹配直接判“未在镜头目录中匹配到”，用户只能自己从头敲。本功能在**精确匹配之外**再加一层“相似建议”。
> 硬约束不变：建议只填名称，**不写 `camera_uuid`、不改 `match_status`、不建立绑定**。

## 1. 匹配分层

| 层 | 方法 | 判定 | 结果字段 |
| --- | --- | --- | --- |
| 1 | 规范化精确匹配（原有） | NFKC + casefold + 去分隔符后完全相等 | `directory_candidates`（带 `match_method=normalized_exact`） |
| 2 | 相似建议（本次新增） | 同形字折叠后的字符串相似度 ≥ 0.78 | `name_suggestions`（带 `score`、`method=homoglyph_folded_ratio`） |

第 1 层保持不变；第 2 层只在有 OCR 名称时计算，最多 3 条。

## 2. 相似度算法（`backend/app/camera_name_match.py`）

1. `normalize_name()`：NFKC → casefold → 去掉空格、`-`、`_`、`·`、括号、标点。中文全角/半角先统一。
2. `fold_homoglyphs()`：把最常混的字母折到数字：`o→0`、`i→1`、`l→1`、`s→5`、`b→8`、`z→2`、`g→6`。
   只折叠这批，避免过度匹配（`Q→0`、`D→0` 之类一律不做）。
3. `name_score()`：规范化完全相同 = `1.0`；否则用 `difflib.SequenceMatcher` 在折叠后的串上算比值。
4. `suggest_names()`：对目录里每个 `active` 镜头的 `display_name` + `aliases`（**不含 `index_code`**，理由见 §4）
   取最高分，按分数倒序取前 3，阈值 `MIN_SCORE = 0.78`。

## 3. 阈值与效果（真实目录实测）

数据：`TrajNexa_Map` 只读库，`cameras_registry` 中 1130 个有名称的镜头。脚本：`backend/scripts` 之外的临时验证（结果如下）。

| OCR 输入 | 期望 | 实测 top-1 | 分数 |
| --- | --- | --- | --- |
| `3-DX-金水路4O号恒利花园门口-向东` | 同名（0↔O） | 同名 | 1.000 |
| `3-DX-金水路40号恒利花园门口-向乐` | 同名（末字错） | 同名 | 0.941（与“-向南”同分并列） |
| `BTS-临桂花生唐红绿灯北囗` | 同名（异体字） | 同名 | 0.923 |
| `大井头村民房l` | `大井头村民房1` | 同名 | 1.000 |
| `清源居民区建设路4O号南` | 同名 | 同名 | 1.000 |
| `岩塘村碧园印烧烤店住宿点`（丢字） | 同名 | 同名 | 0.960 |
| `摄像头1号门口` | 无 | 无（最高 0.353） | — |
| `CAM-99 UNKNOWN GATE` | 无 | 无（最高 0.167） | — |
| `45031200001320` | 无 | 无 | — |

结论：错 1~2 个字符基本都能进 top-3；无关名称最高 0.42，0.78 的阈值留了足够余量。
随机抽 8 个真实名称、每个造 3 种错误，共 24 例，`hit top-1` 22 例；两个 miss 都是“末位方向字被换成 X”这种信息被抹掉的情况，
此时建议里仍包含正确项（top-3 命中），由人挑选。

## 4. 为什么不拿 index_code 做相似度（数据缺陷）

`cameras_registry.index_code` 大量重复：1130 条里有上千条共用 `45031200001310` 之类编号。
如果把编号放进相似度候选，一个编号会同时命中几十台镜头、全部 1.0 分，等于制造误报。
因此相似建议只用 `display_name` + `aliases`；编号的精确匹配仍由原有精确逻辑负责。

## 5. 接口与前端

报告 `camera` 块新增：

```json
"name_suggestions": [
  {
    "camera_uuid": "…",
    "display_name": "3-DX-金水路40号恒利花园门口-向东",
    "matched_value": "3-DX-金水路40号恒利花园门口-向东",
    "ocr_text": "3-DX-金水路4O号恒利花园门口-向东",
    "score": 1.0,
    "method": "homoglyph_folded_ratio",
    "map_camera_id": 9000000000000023,
    "requires_human_confirmation": true
  }
]
```

前端（`AddElementModal` 的「摄像头名称」区）：

- 建议以可点击标签展示 `名称 + 相似度%`，悬停显示对应的 OCR 原文；
- 点击只做一件事：把名称填进输入框，并把状态标成「已采用相似名称，未绑定镜头目录」；
- **不会**调用 `syncCatalogMatch()`，因此不会自动设置 `confirmedCamera`，保存时 `cameraId` 仍为空；
- 标签下方常驻提示：「相似建议只填名称、不建立绑定；确认真实镜头请人工核对后再绑定」。

## 6. 测试

`backend/tests/test_camera_name_match.py`（8 例，全部离线，不连数据库）：

- 规范化忽略全角/分隔符；0/O、1/l 折叠后判为相同；
- 单字错误能命中正确镜头，且 `requires_human_confirmation=true`；
- 别名可命中；无关名称、停用镜头、空输入都返回空；
- `annotate_camera_report()` 加了建议但 `camera_uuid` 仍为 `None`、`match_status` 不变。

前端用拦截报告的方式验证过渲染与点击：标签显示 `…-向东 100%` / `…-向南 94%`，点击后输入框变为 `…-向东`，
状态从「已识别名称，未绑定镜头目录」变为「已采用相似名称，未绑定镜头目录」，没有出现“已匹配镜头目录”。

## 7. 局限（别当成已解决）

- **同后缀多镜头会并列**：`…-向东` / `…-向南` 只差一个字，分数可能相同，界面按目录顺序展示，仍需人从画面判断方向。
- **短名称误报上限低**：名称只有 3~4 个字时，一个字的差异就占 25%，阈值仍可能落入；目前靠“最多 3 条 + 必须人工确认”兜底。
- **只比对名称**：不做画面/位置/朝向一致性校验；真正的绑定仍走 M1c 的 `camera-bindings` 或后续 M1d 参考图校验。
- **目录来源**：建议质量取决于 `cameras_registry.name` 是否规范（人工录入、含方位后缀）。有别名文件 `map_camera_aliases.json` 时会一起参与比对。
