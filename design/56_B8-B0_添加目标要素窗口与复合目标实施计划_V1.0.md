## 0. 决策摘要（必须遵守）

1. **整体窗口采用左 65%、右 35% 的两栏结构**。左侧只负责截图观察、视图控制和目标框选择；右侧按「画面来源 → 当前选中目标 → 可见特征 → 补充说明」顺序完成录入；其他信息统一放「更多信息」。底部固定保存操作。
2. **目标主体与对象类别不是一回事**：用户明确选择一次追踪主要跟踪的对象（人员 / 车辆 / 其他），同一截图可选择零个或多个关联对象；不新增独立的“人车组合”检测类别，不强制合并成单框，不自动为用户决定追踪人还是车。
3. **人物、车辆分别有独立 ROI 和对象 ID**；同一画面中的 `riding` 等关系是带来源和审核状态的独立记录；可生成仅用于观察的组合上下文框，但不能把它直接当 OSNet 人物 ReID ROI。
4. **保存动作对用户只出现一次**：一次性、事务性地保存目标主体、关联对象、关系、来源、属性与审计引用。现有 M4a 观测可以继续作为底层原子证据，不再要求用户先点“保存区域观测”。
5. **模型建议 ≠ 人工真值 ≠ 跨镜头身份确认**。Qwen3-VL-4B 是默认的可选属性提取模型；字段必须明确来源、所属对象、状态和原始证据；`unknown` 不等于“没有”也不等于“不匹配”；WeVisOne-VL 保留模型接口但不作为本轮必需能力。
6. **兼容现有单对象数据、录像和 B8 追踪任务**。旧截图、旧 ROI 和已有工作台元素不得因迁移丢失；M6 仍以指定主目标的观测为起点，关联对象只作为额外证据，不因车辆丢失或改变就终止对人的追踪。
7. **本阶段只重构录入与目标档案**；不会自动启用属性融合、自动确认跨镜头身份或启动持续追踪。后续 B8 由用户显式发起任务。

## 1. 背景、现状与问题

### 1.1 真实业务场景

用户上传一帧骑行者监控截图，需要追踪正在骑车的**人**；车辆能帮助核查其跨镜头出现。另一案件中，用户可能要追踪被盗**车辆**，骑车人只是辅助线索。用户必须能在同一图像同时选中这两个对象，并明确谁是追踪主体，记录当时画面可见的骑乘关系。

### 1.2 已确认的代码现状（基线 `b94cfea`）

| 模块 / 文件 | 当前可复用部分 | 必须处理的缺口 |
| --- | --- | --- |

| `frontend/src/store/workbench.ts` 与 `data/mock.ts` | 元素、特征和时间线接口 | `ElementPayload` 实际仅带单个保存的框及单一 `m4ObservationId`，元素状态部分仍在前端内存 |
| `backend/app/m4_api.py` | 已归属案件的原始截图、校验哈希、单框 `TargetObservation` | `ObservationInput` 只接收 `object_class + bbox_normalized`；无一个目标主体对多个对象、关系的事务保存接口 |
| `backend/app/m6_person_vehicle_relation.py` | 多帧骑乘、靠近、分离等关系候选 | 不能直接把“单张截图人工标注”的骑乘关系伪装成通过多帧运动核验 |

### 1.3 当前窗口暴露的额外错误

- **来源时间冲突**：提供的截图画面顶部时间为 `2026-10-23 15:00:31`，而右侧表单出现 `2020-10-03 15:00:31`；必须保留 OCR 原值与用户修改记录，校验完整日期，不能静默用本机日期补齐。
- **摄像头名称异常**：曾出现 `(name ?? "").trim is not a function`，属于把非字符串值直接交给字符串函数。修复前端的类型守卫及后端数据响应校验，不能仅把错误信息隐藏。
- **模型标签错位**：`Rebucca D-FINE N 候选：人` 是检测来源，不是目标外观特征，必须从“关键特征”值中移除；模型 ID、版本、检测置信度应存技术 provenance。

## 2. 信息架构与布局要求

### 2.1 窗口外形和比例

- 原生模态窗口沿用现有 `BaseModal`，建议宽度占可用视口约 96%–98%、高度约 92vh；内部始终使用 `grid-template-columns: minmax(0, 65fr) minmax(0, 35fr)`。**65/35 是两栏内容宽度比例**，不是左栏固定像素。
- 左、右栏可独立处理溢出：左栏为大图及极简工具栏；右栏独立纵向滚动；底部固定操作栏。小屏不能压缩到不可点击的 100px 缩略图，允许设置最小工作宽度并在容器内横向滚动，不静默改变用户要求的主比例。
- 禁止把“模型检测结果列表 / M4a 历史 / 原始 OCR 表”重新塞入左栏下方占据图片高度。

### 2.2 左侧：仅截图和目标选择（65%）

**保留**：上传 / 更换截图、当前截图预览、放大缩小、平移、适应窗口、重置；点击候选框；手动绘制 / 编辑 / 删除框；重新检测；多个候选叠框时切换与选择；简短状态提示。

**删除左侧独立面板**：检测模型标签墙、关键特征面板、M4a 观测历史、原始识别依据、长篇模型错误详情。

建议工具条：`更换截图 | 选择主目标 | 添加关联 | 手动框选 | 平移 | 放大/缩小 | 适应 | 重置 | 重新检测`。

对象框视觉语义：主目标**蓝色实线**，关联对象**橙色实线**，其他候选**低对比细线**；悬停突出对象类别。图片顶部或底部只显示一句状态，例如“检测到 13 个候选｜主目标 1｜关联 1”。颜色配合文字/图形标识，不能只靠颜色区分。

交互约束：

- 三种互斥模式：`select`（选框）、`draw`（框选）、`pan`（平移）。缩放时框跟随图像，不改变原始坐标；支持 Esc 取消、滚轮缩放、重置视图。
- 候选重叠时，可通过鼠标点击循环、短列表或键盘 Tab 切换；不能因“人员/车辆覆盖”就只能点到最上层。
- 用户将候选设为主目标或关联对象后，**重新检测只更新未确认候选**，不得清空已选框、人工修改的框、属性或关系。用户明确点击“替换此框”才变更已选对象。
- 切换图片 / 案件 / 关闭弹窗时，若有未保存修改，给出保存/放弃确认；重选截图不能误保留上一张图的坐标。
- 失败显示轻量提示（例如“检测失败，可手动框选”）；技术错误详情进“更多信息”，绝不将“模型调用失败”显示成“没有目标”。

### 2.3 右侧：按用户录入顺序组织（35%）

**A. 画面来源**：顶部依次为 OCR 原始时间 / 日期+时刻编辑、标记未知；OCR 摄像头名称直接填入可编辑文本框；已匹配 Map 台账摄像头采用下拉项（含名称、UUID、匹配方式/核验状态）。只有用户核验之后才标记已绑定。OCR/台账冲突就地用简短警告，不直接阻止保存草稿。

**B. 当前选中目标**：两个并列小卡片——左为**主目标**、右为**关联对象**，包含标题、截图裁剪缩略图、类别、审核标记及 `重新选择`；中间 `⇄` 用于在存在合法关联时交换主次。卡片内部去掉大段说明和重复属性。关联对象可为空，可添加；超过 1 个时右卡切换当前关联对象，数据层支持 0..N。

- 用户必须先选择主目标；关联对象必须由用户显式选中，不会从同一帧默认自动合并。
- 点击主卡或关联卡，右侧“可见特征”切换编辑对应对象；点击缩略图可在左图高亮其框。
- 交换主次需确认；保存对象身份不变，仅改变 `primary_object_id` 和角色。换成车辆为主时，后续追踪不能继续读取人物 ReID 作为主对象的身份特征；旧模型向量/上下文不被静默删除，但标记为不适用于新主目标。
- 关系可从小型下拉项选择 `riding / passenger / pushing / nearby / carrying / unknown`，只对当前合法的对象类型组合显示有意义的选项；保留“人工在此帧观察到/待核验”状态。车辆可以是关联对象，不能通过“人车同框”自动断定正在骑乘。
- 可选“查看组合画面”只展示两个框的外接上下文区域；组合框是 **context evidence**，不得用作 `person_reid` 的人物 ROI。

**C. 可见特征**：默认紧凑行式编辑；人员默认 `上衣 / 下装 / 鞋 / 随身物`，车辆默认 `车辆类型 / 车身颜色 / 车身标识或附属物`；切换卡片后展示该对象的属性。每个字段有值/未知/不适用状态与来源（人工 / AI 提议），在有限宽度内不展开冗长解释。支持人工覆盖、恢复提议值。

- Qwen3-VL-4B 可在目标确定后按需分析**人物裁剪**及**必要时的关联场景裁剪**；不可对每个候选自动调用、不可假定模型输出已核实。
- AI 提议需存 `model_id/version`、prompt 版本、crop/region、字段原文、创建时间和 `model_proposed`；人工确认改为 `human_verified`，拒绝则记 `human_rejected`，原输出仍可追踪。
- `known / unknown / not_applicable` 是观测语义；“未看见同伴”且画面遮挡或不完整应是 `unknown`，不得自动填写 `no`。Qwen 在此类字段曾出现幻觉，需明确保留无依据字段为空/未知的通道。
- 禁止把检测器名称、模型类别、置信分等元信息作为“上衣”等人类可见属性。

**D. 补充说明**：单个简洁备注框（一次提交，关联对象备注可扩展到更多信息），不强制长篇说明。

**更多信息（默认折叠）**：高级属性、M4 历史记录、原图/ROI 的 SHA、OCR 原文及来源、模型/权重版本及执行错误、关联关系/审核历史、时钟和摄像头绑定质量。此处信息**可查看、可追溯，但不是主编辑流程**。

**底部固定**：`取消 | 保存并继续添加 | 保存目标要素`；按当前是否正在编辑改为 `保存修改`。未完成必填内容时按钮不可用并给出原因；成功仅执行一次服务端事务，不再暴露“先保存 M4a 再保存目标”的双层操作。

## 3. 复合目标领域模型

### 3.1 核心概念

- **TargetGroup / TargetElementGroup（目标要素组）**：一次用户录入的目标档案集合，归属单一 `case_id` 和原始 `media_id`。
- **TargetObject（对象）**：画面中被选择的人员、车辆或其他可见实体；每个对象有稳定 `object_id`、`object_class`、独立 ROI；对象可出现/消失、可不适用于追踪主特征。
- **Primary（追踪主体）**：一个目标要素组恰好一个主对象 `primary_object_id`；由用户决定追踪谁。关联对象为 `associated`，默认不是独立追踪任务。
- **ObjectRelation（对象关系）**：`subject_object_id + predicate + object_object_id`，附有图像/时间、核验方式与状态；单帧 `image_observed` **不是**多帧 `temporal_verified`，关系可能随时间转变。
- **AttributeEvidence（对象属性）**：每字段包含归属对象、语义值、known/unknown/not_applicable、提议/核验状态、来源 ROI / 模型及修订事件；未知不等于否定。
- **Observation（观测）**：将对象与某一图像来源、可选摄像头时间、原始 ROI 连接；一次录入包含一个或多个独立观测。原 M4a `TargetObservation` 保留，不将其一条记录当作“整组对象”。

### 3.2 示意结构（字段与坐标仅供约定，不是真实截图测量）

```json
{
  "schema": "target-element-group/1",
  "case_id": "CASE-UUID",
  "media_id": "MEDIA-UUID",
  "primary_object_id": "P001",
  "objects": [
    {"id": "P001", "object_class": "person", "role": "primary", "bbox_norm_xyxy": [0.38, 0.31, 0.44, 0.42], "source": "human_selected", "m4_observation_id": null},
    {"id": "V001", "object_class": "vehicle", "role": "associated", "bbox_norm_xyxy": [0.36, 0.37, 0.46, 0.47], "source": "human_selected", "m4_observation_id": null}
  ],
  "relations": [
    {"subject_id": "P001", "predicate": "riding", "object_id": "V001", "status": "image_observed", "temporal_verified": false, "evidence_media_id": "MEDIA-UUID"}
  ],
  "attributes": [
    {"subject_id": "P001", "name": "garment_color", "value": null, "observation_status": "unknown", "review_state": "unknown", "source": "human"},
    {"subject_id": "V001", "name": "vehicle_type", "value": "scooter", "observation_status": "known", "review_state": "model_proposed", "source": "qwen3vl4b"}
  ],
  "source": {"capture_at": null, "time_status": "unverified", "camera_uuid": null, "camera_status": "unverified"},
  "revision": 1
}
```

核心约束：`primary_object_id` 必须在该组对象中；对象与关系的两个端点必须存在、互不相同、与同一案件/图片绑定；每个对象 bbox 范围是 `[0, 1]` 且 `x1 < x2`、`y1 < y2`；关系不能自行建立跨镜头身份；任何模型输出不自动写 `human_verified`。

### 3.3 场景与追踪语义

| 起始选择 | 之后变化 | M6 正确行为 |
| --- | --- | --- |
| 人为主、两轮车为关联 | 在下一镜头仍骑原车 | 人物 ReID/时空搜索继续，车辆外观是辅助线索 |
| 人为主、车辆为关联 | 后续下车步行 | 人仍为主，车辆关系变为历史，不以“无车”排除人 |
| 车辆为主、人为关联 | 车换了骑行人 | 车辆仍是追踪主体；人员不是车辆身份替代品，需要适用的车辆特征链 |
| 仅有人物 | 检测不到车 | 单对象合法保存，不阻塞分析 |
| 多人同框或多人同车 | 关系不清 | 允许不加关系，或记 `unknown`，不得自动配对 |
| 看不清属性 | 帧中有其他颜色的车 | 目标属性为 `unknown`；不能将相邻车辆颜色写到当前主体 |

## 4. 后端数据与接口实施方案

### 4.1 数据持久化（建议增量迁移，避免重建 M4）

按当前 SQLAlchemy / Alembic 迁移体系，增加三类基础实体及必要的关联/事件实体，名称可按团队命名习惯落地：

1. `target_element_groups`：组 ID、`case_id`、`media_id`、`primary_object_id`、来源时间/摄像头验证状态、状态、版本、创建/修改及审计字段。
2. `target_element_objects`：对象 ID、组 ID、类别、角色、原图归一化 ROI、`m4_observation_id`、检测/人工来源、版本；可允许 0..N 关联对象，但组内必须恰好一主。
3. `target_object_relations`：关系 ID、组 ID、两个对象 ID、关系枚举、`image_observed`/`model_proposed`/`human_verified`/`rejected` 状态，是否多帧核验，来源图像/时间、审核事件。
4. `target_object_attributes`（或复用已有目标档案中的结构化属性表）：字段名、值、`observation_status`、`review_state`、对象 ID、证据区域、模型与提示词 provenance、创建及修订事件；尽量使用可查询索引和独立 JSON 原文，避免只存前端拼接的文本。

原有 M4a 观测可以作为每个对象独立 ROI 的持久凭据：新组保存时由后端统一创建/引用这些观测，**不新增混合 `person_vehicle` 作为 `object_class`**。旧记录/旧元素升级为单对象组可以采用按需适配或后台迁移，保留原 ID 和引用，避免破坏已存在 B8 任务。

### 4.2 API（建议新增，具体路径以仓库统一路由规则为准）

| 方法与路径 | 用途 | 关键要求 |
| --- | --- | --- |
| `POST /api/v1/cases/{case_id}/target-groups` | 原子保存目标组 | 输入 `media_id`、primary、objects、relations、attributes、source；一次事务校验同案；支持幂等键 |
| `GET /api/v1/cases/{case_id}/target-groups` | 查询本案目标档案列表 | 不跨案，包含单/复合目标区分与预览信息 |
| `GET /api/v1/cases/{case_id}/target-groups/{group_id}` | 回填编辑窗口 | 返回全部对象、关系、来源、属性、版本、审核状态 |
| `PATCH /api/v1/cases/{case_id}/target-groups/{group_id}` | 编辑主次、ROI、关系及属性 | 使用修订号 / ETag 乐观锁；保存历史，不能静默覆盖 |
| `POST /api/v1/cases/{case_id}/target-groups/{group_id}/attribute-analysis` | 异步或按需提交 AI 属性提议 | 服务端登记模型，最小化使用单个 ROI，不能写入人工已确认字段 |

新 API 必须引用服务器已归属案件的截图和对象，不接受任意磁盘绝对路径、任意外部模型地址或跨案件对象 ID。身份授权控制需要在 B8 生产部署前与案件权限统一落地；此计划不将“传个 case_id”当成已完成权限验证。

对外字段不应把 `camera_name` 字符串“相似”映射成已核实的 `camera_uuid`；OCR 原始值、候选和人审后的绑定分别保存。时间原值、时区、修改人、核验状态、时钟不确定度都要有可查询来源。

### 4.3 与现有 B8 追踪接口的连接

- `POST /cases/{case_id}/tracking-runs` 的创建输入可新增 `target_group_id`（或兼容现有 `observation_id`）：后端从**主对象**解析真实 `TargetObservation` 作为 anchor；不允许前端随意提供其他对象冒充主体。
- 保留现有单个 `observation_id` 路径作为兼容入口；新组中若 `primary` 为 `person`，沿用人物 ROI/OSNet；若为车辆，必须检查当前实际可用的车辆检索链，不应调用人物 ReID 冒充车辆身份特征；缺少车辆主体能力时明确标示未支持/降级状态。
- 关联对象和单帧关系进入证据上下文；不可自动提升候选身份分数，不会把一次截图的 `riding` 当作 M6 多帧骑乘核验通过。
- 任务快照固定引用的目标组版本，后续编辑不应悄悄改变正在执行的追踪任务。

## 6. 质量、安全与回归要求

### 6.1 服务端校验

- 每个组至少一个对象，恰好一个主对象；任何关系只能引用本组对象；`media_id` 必须归属当前案件且文件哈希匹配。
- 坐标和图像裁剪按原图归一化值校验，拒绝 NaN / 无效框 / 越界；不接受客户端提供的任意文件 URL。
- 属性枚举与字段类型校验；`unknown` 值不能携带看似确定的事实；`not_applicable` 与“看不清”严格分开。
- 模型 `visible=true` 不是人工已核验；模型输出来源、审核人、审核时间不能伪造；模型原始结果与人审修订分开留存。
- 并发/幂等：重复提交不重复创建多个要素组；版本冲突返回可理解的错误，原始档案不丢失。

### 6.2 测试矩阵

| 用例 | 预期 |

| 只有一个行人 | 保存单目标、恢复同一个框、可启动既有人物追踪路径 |

## 7. 风险、边界与不做事项

- **风险：双重保存/内存状态残留**。先约定服务端事务契约，再接前端；不沿用“弹窗里存 M4 再存内存元素”的旧体验。
- **风险：属性串色/错归属**。衣物、车辆、同行关系必须关联到 `subject_id` 和证据区域，不得因为整张图片里有红车就写目标车色为红。
- **风险：模型误导**。Qwen 在 unknown 场景可能坚持输出颜色或同行 `no`，默认“建议待核验”，手工改后不得被自动覆盖。
- **风险：历史数据不兼容**。新增表及适配层、先迁移后切 UI；保留旧路由/旧观测读取以支持历史案件。
- **风险：权限与审计**。单一案件 ID 不是授权凭证；正式对外部署要完成身份认证、访问控制与操作者审计，最小化处理无关人员/车辆。
- **本轮不做**：重训练“人车组合”检测模型、WeVisOne 深度研究、自动属性融合排序、从一张截图证明真实运动方向、自动替用户确认人车关系、替代独立的 TrajNexa_Map GIS 编辑系统、一次性重写 M6 追踪算法。
