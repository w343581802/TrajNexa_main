# 26 能力地图与复用契约（写新功能前先查这张表）

> 全部设计文档索引见 [README.md](README.md)。本文是硬约束，不是参考。第 2 节的契约违反一次就是一次返工；第 3 节的检查清单没走完，不要开新组件、新接口。

> ## 约束 0（最高优先级，优先于 C1–C12 与本文其余全部条款）：当前交付物是技术验证 Demo，不是生产系统

**性质**：项目现阶段的目标是**把技术路线演出来、验出可行或不可行**，不是交付可运营的生产系统。
判断某件事该不该做，按这个顺序问，答案在前一条就不用看后面：

1. **演示路径能不能走通、能不能被看见**（界面上有没有入口、点了有没有结果）；
2. **技术有没有被验证**（有实测数据、命令输出、对照结论，而不是"看起来对"）；
3. **演示时会不会中断或卡死**；
4. 最后才是代码质量、并发、边界条件、工程债。

**该做**：把已有能力接通到界面上；给每个验证点留下可复跑的证据；给演示配开关与降级（模型不可用→规则，服务不在→提示而非卡死）；准备预置数据与兜底帧。

**不该做（除非它直接卡住演示）**：不追非演示路径上的 bug；不为未来扩展做重构；不补 RBAC / 权限体系；不做迁移治理、并发压测、性能上限；不为"正确性完备"加防御代码；不提前还"迟早要还的技术债"。

**已知缺陷的处置**：写进文档（如 [33](33_M3代码审核与修复记录.md)）备案即可，等它出现在演示路径上再修。缺陷清单不是待办清单。

**仍然有效的约束**：C1–C12 全部有效（尤其是「一个取帧入口」「一个识别结论结构」「人工结论只进不退」）；模型输出一律只能是待核实观测或建议，不得当成事实。

**禁止**：把 Demo 结论说成生产结论；用演示界面"看着对"代替实测证据；把外部 README 的功能声明写成已实现。

## 0. 为什么有这份文档

2026-10-30 一轮开发里出现过两次返工，原因都不是技术难，而是**没有先查已有能力**：

1. 给录像资源新造了「确认 / 排除」审核弹窗，而产品要的是复用已有的「左截图 / 右表单」核对窗 —— 做完被推翻重做；
2. 截图接口直接取 0.5 秒那一帧，而录像开头是花屏 —— 界面上出现一张花屏图，还得回头补坏帧过滤。

同一个仓库里已经有视频命名、添加要素、录像资源三套管线，它们**共用同一条取帧与识别链路**。
新功能的正确做法几乎总是：找到这条链路，从中间接进去，而不是在旁边另起一套。

## 2. 契约

### C1 取帧只有一个入口

- **契约**：任何要视频画面的功能，必须走 `overlay_identity.grab_evidence_frame(path, offsets=...)`；不得直接调 `ffmpeg`、不得直接调 `overlay_ocr.read_frame`。
- **为什么**：取帧要处理快速 seek / 精确 seek 回退、灰占位帧、花屏帧三件事，散开写必然漏。
- **检查**：`grep -rn "read_frame(" backend/app/` 只允许出现在 `overlay_ocr.py` 与 `overlay_identity.py`。

### C2 识别结论只有一个结构

- **契约**：摄像头名称、拍摄时间、来源、告警一律来自 `OverlayIdentity`（`identify_video` 的返回值），字段名为 `camera_name` / `name_source` / `name_status` / `capture_time` / `time_source` / `warnings`。
- **为什么**：扫描、命名、添加要素三处必须给出同一份结论，否则同一段录像在三个页签里说法不一致。
- **检查**：新增页签先看 `overlay_identity.py` 的 `as_dict()` 有没有你要的字段，没有再扩展它，不许自造。

### C3 名称匹配只有一个口径

- **契约**：名称 → 摄像头只能走 `recordings.match_camera(names, index, catalog)`：**唯一精确命中才自动绑定**，其余只给 `suggestions`，不许自动猜。
- **为什么**：误绑比不绑贵得多；候选是给人看的，不是给流程用的。
- **检查**：`grep -rn "match_camera" backend/app/` 之外不得出现自写的相似度匹配。

### C4 名称来源词表固定

- **契约**：`name_source` 只能是 `none` / `ocr` / `filename` / `manual`；`time_source` 只能是 `ocr` / `filename`。前端文案见 `nameSourceLabel`。
- **为什么**：来源决定可信度与界面提示（文件名兜底必须显式说「未经角标确认」）。

### C5 匹配状态词表固定

| 值 | 含义 | 界面文案 |
| --- | --- | --- |
| `unscanned` | 还没扫 | 未扫描 |
| `no_name` | 没有名称 | 无名称 |
| `ocr_disabled` | OCR 未启用 | OCR未启用 |
| `catalog_unavailable` | 台账不可用 | 台账不可用 |
| `matched` | 唯一精确命中并绑定 | 已匹配 |
| `ambiguous` | 同名多台 | 同名多台 |
| `unmatched` | 有名称但无命中 | 未匹配 |
| `review_rejected` | 历史人工排除 | 已排除 |
| `scan_error` | 扫描出错 | 出错 |

**契约**：新增状态必须在 `recordings.py`、`recording_api.py`、`frontend/src/services/mainApi.ts`、`BottomDock.vue` 的 `matchLabel` 四处同时登记。

### C6 人工结论只进不退

- **契约**：`review_kind in ('confirmed', 'rejected')` 的行，自动扫描与「重新匹配摄像头」都不得覆盖其名称/绑定；人工再改只能通过核对弹窗写入。
- **为什么**：人工核对是唯一的真相来源，自动流程回滚它等于让人白干。

### C7 录像资源只读

- **契约**：`recordings.py` / `recording_api.py` 不得对录像文件做任何写操作（改名、删除、移动、转码）；只允许读、`stat`、抽帧。缓存图写到 `storage/recording-frames`，不得写回录像目录。
- **检查**：新增代码里出现 `unlink` / `remove` / `rename` / `shutil.move` 作用于录像路径即为违反。

### C8 截图必须过滤坏帧

- **契约**：任何对外展示的视频截图，必须经过 `frame_is_blank` + `frame_is_broken` 过滤；开头花屏时按 `PREVIEW_OFFSETS` 往后找（0.5/2/4/8/15/30/60 秒），都坏则明确报 `frame_unavailable`，**不产出坏图**。
- **为什么**：花屏图看起来像系统坏了，比没有图更糟。

### C9 人工核对窗只有一套

- **契约**：核对识别名称的界面只有一个 —— `RecordingClipNameModal.vue`（左画面截图、右文件名 + 识别名称输入 + 备注）。视频命名的「手动命名」保持改文件名的语义，两者不合并、也不许再开第三个。

### C10 错误返回统一

- **契约**：接口错误一律 `{"error": {"code", "message", "details"}}`，用 `recording_api.fail()` 抛出；`code` 用英文短横线小写，`message` 是给人看的完整中文句。

### C11 迁移用 alembic

- **契约**：建表/加列一律新增 `backend/alembic/versions/NNNN_*.py` 并 `alembic upgrade head`；不得用 `create_all` 兜底。`migrate` 容器跑完才允许 api/worker 启动。

### C12 前端只走 /api 代理

- **契约**：前端请求一律相对路径 `/api/v1/...`，由 Vite 代理到 api 容器；组件里不得出现 `127.0.0.1:8010` 之类硬编码。

## 3. 新增功能前的检查清单

开工前逐条回答，回答不了就先读代码：

1. **这件事是不是已经有人做了？** 先查第 1 节表，再 `grep` 关键词（取帧、匹配、识别、审核）。
2. **数据从哪来、写哪儿？** 视频目录一律只读；写只看 `storage/`、数据库表。
3. **识别结论用 `OverlayIdentity` 吗？** 不是就先说明为什么不能复用。
4. **匹配用 `match_camera` 吗？** 自己做相似度就是违反 C3。
5. **界面是否复用现有窗口？** 左图右表单的核对、批量表格、路径输入三种版式已经存在。
6. **有没有新增状态词/来源词？** 有就按 C4/C5 四处同步登记。
7. **截图会不会是花屏？** 走 C1 + C8。

## 4. 反例复盘（两次返工）

| 现象 | 当时做法 | 正确做法 | 契约 |
| --- | --- | --- | --- |
| 审核窗被推翻 | 新写「确认 / 排除」弹窗 | 左截图 / 右识别名称的核对窗 | C9 |
| 界面出现花屏图 | 直接取 0.5 秒那一帧 | `grab_evidence_frame` + `PREVIEW_OFFSETS` | C1 / C8 |
| 台账明明有 25 台却说不可用 | 前端按 `status == "ok"` 判断 | 后端状态值是 `available`，按词表判断 | C5 |

## 5. 契约的自动化守卫

`backend/tests/test_architecture_contracts.py` 用源码静态检查兜住最容易复发的那几条：

- 取帧函数只有一个定义、`read_frame` 只在两个文件里被调用（C1）；
- `grab_evidence_frame`、`match_camera`、`frame_is_broken` 各自只有一个定义（C1/C3/C8）；
- `recordings.py` 不出现删除 / 移动 / 改名调用（C7）；
- 前端 `RecordingClip*Modal.vue` 只有一个（C9）。

其中依赖 `design/` 与 `frontend/` 目录的两条检查，在容器里跑测试时会跳过（容器只挂了 `backend` 与 `storage`），
需要时在宿主机 `cd backend && pytest -q` 补跑一次。

改动这些契约时，**先改本文档，再改测试，最后改实现**。
