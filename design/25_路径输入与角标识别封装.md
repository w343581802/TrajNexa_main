# 25 · 复用封装：本地路径输入 + 时间/摄像头名称识别

> 本文记录两件「到处都要用、必须只有一份实现」的事，以及它们怎么接到录像资源、
> 视频命名工具、添加要素三处。前置阅读：[24 视频命名工具](24_视频命名工具.md)、
> [22 录像资源接线与添加要素截图化](22_录像资源接线与添加要素截图化.md)。

## 1. 为什么要封装

同一套能力被三处各写了一遍，已经开始走偏：

| 能力 | 改造前 | 问题 |
| --- | --- | --- |
| 前端传路径 / 后端读本地文件 | 视频命名工具自己一套（\`_translate_host_path\`、\`_resolve_input\`、\`_collect\`）；录像资源只认「相对录像根目录」 | 录像资源挂载目录根本没法填 \`G:\\测试数据\\视频\\正常\`，只能一级级点 |
| 时间 + 摄像头名称识别 | 录像扫描、视频命名、截图预检各写一遍抽帧 + OCR + 解析 | 灰占位帧修复、名称牌正则、文件名时间兜底每次都要改三处 |

现在收成两个模块，调用方只做「取结论 + 落自己的表」：

* \`backend/app/media_inputs.py\` —— 路径输入口径
* \`backend/app/overlay_identity.py\` —— 时间 + 摄像头名称识别口径

## 2. media_inputs：前端传路径，后端读本地文件 / 目录

### 2.1 契约

前端**只传路径文本**，不传文件；后端负责翻译成容器内可读的路径。

| 输入形态 | 例子 | 解析方式 |
| --- | --- | --- |
| 宿主机绝对路径 | \`G:\\测试数据\\视频\\正常\` | 按 \`MEDIA_INPUT_PATH_MAP\` 换成容器挂载点 |
| 容器绝对路径 | \`/data/videos/正常\` | 直接使用 |
| 相对路径 | \`正常/某摄像头目录\` | 按 \`default_root\` 解析 |
| 目录 | 上面的目录 | \`recursive\` 决定是否递归 |
| 单个文件 | \`...\\3-DX-中仁路98号-球_20261023145955.mp4\` | 只处理这一个（录像资源取它所在目录） |

固定行为：统一分隔符（\`\\\` 与 \`/\` 都认，盘符大小写不敏感）、去掉首尾引号、
跳过隐藏项（\`.开头\`的目录/文件）、顺序稳定、结果去重、\`limit\` 上限。

### 2.2 配置

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| \`MEDIA_INPUT_PATH_MAP\` | 空 | 留空自动沿用 \`VIDEO_NAMING_PATH_MAP\`，已有部署不用改 |
| \`MEDIA_INPUT_ROOTS\` | 空 | 留空自动沿用 \`VIDEO_NAMING_ROOTS\`；配了就只能访问这些根目录 |
| \`MEDIA_INPUT_ROOT\` | 空 | 留空自动沿用 \`VIDEO_NAMING_ROOT\`（\`/data/video-library\`） |

**同一个宿主机目录可以映射到不同挂载点**：\`translate_host_path(..., container_root=...)\`
给录像资源用，把 \`G:\\测试数据\\视频\\正常\` 指到**只读**的 \`/data/videos/正常\`；
视频命名工具不传，落到**可写**的 \`/data/video-library/正常\`。权限边界跟着挂载点走。

### 2.3 错误码

\`InputPathError(code, message)\`，与视频命名工具的历史错误码一致：

\`empty_path\` / \`source_not_found\` / \`path_not_allowed\` / \`unsupported_video\` /
\`no_videos\` / \`too_many_files\`。

录像资源再映射成自己的两个码（\`recording_path_invalid\` / \`recording_path_missing\`），
前端文案不用换。

## 3. overlay_identity：时间 + 摄像头名称

### 3.1 结论形状

\`identify_video()\` / \`identify_image()\` 都返回 \`OverlayIdentity\`：

\`\`\`json
{
  "capture_time": "2026-10-23T14:59:57",
  "time_source": "ocr",
  "camera_name": "3-DX-中仁路98号-球",
  "name_status": "structured_osd_candidate",
  "names": ["3-DX-中仁路98号-球"],
  "ocr_status": "ran",
  "duration_seconds": 1800.0,
  "frame_offset": 0.5,
  "warnings": []
}
\`\`\`

口径（与 M1b / M1c 一致，**不猜身份**）：

* 只读开头几秒：\`IDENTITY_OFFSETS = (0.5, 2.0, 4.0)\`，读到「时间 + 名称」立刻停
  ——批量扫几千段录像时，多读一帧就是多一次 ffmpeg seek；
* 时间**角标优先**，角标读不出才退回文件名 14 位时间戳并标 \`time_source='filename'\`；
* 摄像头名称只是**候选**，不写 \`camera_uuid\`、不宣称身份，台账匹配交给 \`recordings.match_camera\`；
* ffmpeg 的灰占位帧由 \`overlay_ocr.read_frame\` 过滤成 \`None\`，一帧都拿不到就是 \`no_frame\`；
* 任何一步失败都显式降级并写进 \`warnings\`，绝不把失败报成「识别成功」。

\`ocr_status\` ∈ \`ran / disabled / unavailable / error / no_frame / not_checked\`。

### 3.2 对外函数

| 函数 | 用途 |
| --- | --- |
| \`identify_video(path)\` | 录像开头几秒（扫描 / 命名共用） |
| \`identify_image(path 或 ndarray)\` | 截图（添加要素用，不落盘） |
| \`identity_from_report(result)\` | 把已有 M1b 报告归一成同一份结论，**不二次 OCR** |
| \`grab_evidence_frame(path)\` | 证据截图：按 \`EVIDENCE_OFFSETS = (0.5, 2.0, 4.0, 8.0, 15.0)\` 多试，取不到返回 \`None\`（不产出假截图） |
| \`probe_duration\` / \`filename_start\` | 时长探测 / 文件名时间戳，原 \`recordings\` 的同名函数仍导出，老调用方不用改 |

## 录像时长识别（probe_duration）

录像资源**不识别结束时间**：每段只存 `start_local`（OCR 角标 / 文件名兜底）和 `duration_seconds`（ffprobe），覆盖卡片按 `start + duration` 绘制，结束即起点加时长，无独立结束时间字段。

时长读取 `probe_duration` 采用多级方案：

1. **轻量元数据**：跑一次 `ffprobe -select_streams v:0 -show_entries stream=duration,avg_frame_rate + format=duration`，取视频流时长（干净文件与容器时长一致，约等于录制时长）。
2. **坏数据精算**：当容器/视频流时长任一 ≥ 24h、缺失、或相差 1.5 倍以上时（DVR/导出工具把时长写成整个会话跨度，例如 30 分钟视频写成 27 小时且 format 与 stream 完全相等），加 `-count_packets` 数全包，用 `包数 / avg_frame_rate` 得可解码时长。
3. **文件名兜底**：以上两步都拿不到时（帧率 0/0、时长全缺的极端文件），解析文件名「至」字前后两个 14 位时间戳，求差值作 estimate（数据来自导出方命名）。

关键点：
- 判定合法时长上限 24h，超过即视为坏数据走精算/兜底，防止 27h 之类坏值直接入库。
- 扫描对「大小/修改时间未变」的文件默认跳过（性能），但时长为 None 或 ≥2h 的旧记录会顺手重算修正——这是本次修复后老库里 12 条 428~1424 分钟坏记录清零的原因。
- 文件名兜底结果仅来自命名，若有二义（例如「至」前不是开始时间）返回 None，不强行猜测。

## 文件名兜底与识别名称核对（含「重新匹配摄像头」）

录像资源解决三个问题：**角标读不到名称时怎么办**、**人工怎么把名称改对**、**台账变了怎么重算**。

### 1. 文件名兜底（只兜底、不冒充识别）

`overlay_identity.filename_camera_label` 从文件名取「第一个 14 位时间戳之前的那一段」作为名称候选：

- `1-LT-桂康路正通路口-向北_20261023145955至20261023153024.mp4` → `1-LT-桂康路正通路口-向北`
- `东门球机A_20261025180000.mp4` → `东门球机A`
- `20261025180000.mp4`（无前缀）→ `None`，不产生垃圾候选

执行顺序固定在 `identify_video` 末尾：**角标 OCR 读到名称就不动**；只有读不到才用文件名标签，
并打标 `name_source="filename"`、`name_status="filename_hint"`，同时在 warnings 里写明
「名称来自文件名兜底，未经角标/人工确认」。

两个明确的边界：

- OCR 引擎未启用（`ocr_status == "disabled"`）**不算读不到**：保持名称空、`match_status="ocr_disabled"`，
  避免把文件名当成识别结论。
- 文件名兜底名称同样只走 `match_camera` 的「唯一精确命中才绑定」口径，其余只给建议。

### 2. 核对识别名称（左截图 / 右名称，改完自动匹配）

片段行的「审核」打开核对弹窗，沿用视频命名「手动命名」那套两栏布局：

- **左侧**：这段录像的画面截图（`GET /api/v1/recordings/clips/{id}/frame`，
  复用 `grab_evidence_frame` 抽帧，按片段缓存在 `storage/recording-frames`，取不到画面就明确报 `frame_unavailable`，不产假图）；
  复用 `grab_evidence_frame` 抽帧，按 clip 缓存在 `storage/recording-frames`，取不到画面就明确报 `frame_unavailable`，不产假图）；
- **右侧**：文件名、所在目录、**识别名称输入框**（默认填当前名称，可直接改）、可选核对备注；
- 改名称时前端用台账本地即时预览：**唯一精确命中显示「将绑定摄像头」**，相近名称给可点击的候选，没有候选就提示「保存后记为未匹配」。

保存走 `POST /api/v1/recordings/clips/{id}/name`：

1. 后端按台账重新 `match_camera`（唯一精确命中才绑定，其余只给建议），不重新读视频、不跑 OCR；
2. 写入 `name_source="manual"`、`review_kind="confirmed"`、`reviewer_note`（有备注才写）；
3. 名称为空 = 解除绑定（`match_status="no_name"`）。

#### 截图必须避开花屏帧

DVR 导出的长录像开头常有几秒到十几秒是**花屏**（解码缺参考帧：整片灰、大块纯白三角、彩色通道几乎为 0）。
实测 `桂康路94号侧墙北_20261023145959…mp4`：0.5s / 2s / 8s / 15s 全是花屏，30s 才正常；
直接取 0.5s 就会把花屏当「开头截图」。

`overlay_ocr.frame_is_broken` 用两个特征判坏帧（阈值来自实测：健康画面 16×16 纯色块占比 ≤ 0.27、饱和度 35~71；
花屏帧块占比 0.45~0.95、饱和度 0~0.7）：

- 纯色块占比 ≥ 0.60 → 坏帧；
- 纯色块占比 ≥ 0.45 且平均饱和度 < 8 → 坏帧。

`grab_evidence_frame` 与 `_video_frame` 都会跳过坏帧（`_video_frame` 还会再退回精确 seek 复核一次），
所以 OCR 也不会再从花屏里读出乱码名称、退回文件名兜底。
人工核对弹窗另外用 `PREVIEW_OFFSETS = (0.5, 2, 4, 8, 15, 30, 60)` 往后找，
开头 15 秒全是花屏时也能给到 30 秒那张干净画面；截图缓存文件名带 `-v2` 后缀，跳过坏帧后旧坏图自动失效。

**只改扫描结果，不动录像文件与文件名**——录像资源仍是只读输入。

保护点在 `scan_source`：文件未变走 skip 分支；文件变了也只更新时长/时间/OCR 状态，
`name_source` / `camera_name` / `camera_uuid` / `match_status` / `match_suggestions` 仅在 `review_kind == "none"` 时接受自动结果。

### 3. 重新匹配摄像头

`POST /api/v1/recordings/sources/{source_id}/rematch`（录像资源每个目录行的靶心按钮）：

- **不重新读视频、不跑 OCR**，只用库里已有的名称对照当前台账重算绑定，秒级返回；
- `camera_name` 为空的行（角标与文件名都没读到的历史记录）先用文件名兜底出候选，标 `name_source="filename"`；
- `review_kind` 非 `none`（人工改过名称）的行整体跳过，返回值里单独计 `human_kept`。

返回 `{updated, unchanged, human_kept}`，前端 toast 直接显示三项计数。

### 4. 真实数据实测（2026-10-30）

`29` 与 `正常` 两个真实目录共 36 段：

- 6 条无名称记录里 5 条从文件名还原出名称，其中 3 条按台账唯一命中自动绑定；
  剩下 `3-DX-中仁路孔明园E40栋-向北`、`桂康路94号侧墙北` 给出候选等待人工核对（不硬猜）；
- `matched` 由 17 升至 20；人工改过名称的片段在重新匹配时计入 `human_kept`，名称不被回滚；
- 截图接口在 4K 片段上返回 457 KB JPEG；名称改成台账名称后立即 `matched` 并带上正确 `camera_uuid`，改回原名恢复 `unmatched`；
- 全程未触碰任何录像文件，接口只读目录与台账。
