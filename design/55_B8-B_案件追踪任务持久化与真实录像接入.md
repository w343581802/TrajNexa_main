# 55｜B8-B：案件追踪任务持久化与真实录像接入（V1）

版本：B8-B / 2026-11-04
分支：`feat/b8-tracking-workbench`
状态：**已实现可启动、可查询、可暂停/取消、可断点续跑的案件追踪任务**；工作台前端接线（B8-C）尚未开始。

## 1. 本批解决的问题

| B8-B 目标 | 本批实现 |
| --- | --- |
| 摆脱实验文件依赖 | 起点只从案件内 `TargetObservation`、`RecordingClip` 读取；worker 按 clip 随时间窗解码真实视频，不再读 truth_package、导出帧目录或 /work 路径 |
| 持久化追踪任务 | 新增 `tracking_runs`、`tracking_windows`、`tracking_candidates`、`tracking_review_events`；进度写 `progress_json`，重启后从未完成窗口继续 |
| 前端可用真实数据 | 提供按案件隔离的读取 API（运行状态、窗口、候选、审核事件）；前端替换模拟状态留到 B8-C |

## 2. 数据模型

| 表 | 作用 | 关键约束 |
| --- | --- | --- |
| `tracking_runs` | 一次追踪任务 | `case_id` 外键；`anchor_json` 保存服务器核实的起点快照；`scope_json` 保存预算；`progress_json` 保存已分析窗口 |
| `tracking_windows` | 每个实际分析的镜头/时间窗 | 记录 clip、窗口、轨迹数、实测成本、失败原因 |
| `tracking_candidates` | 候选轨迹 | `(run_id, candidate_key)` 唯一；默认 `identity_status=candidate_unverified` |
| `tracking_review_events` | 人工审核 | append-only；approve/reject/revoke 都新增一行，不覆盖历史 |

## 3. HTTP 契约

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/v1/cases/{case_id}/tracking-runs` | 创建排队任务（201） |
| GET | `/api/v1/cases/{case_id}/tracking-runs` | 任务列表 |
| GET | `/api/v1/cases/{case_id}/tracking-runs/{run_id}` | 任务详情（含进度、计数、error） |
| GET | `.../candidates` | 候选（含 `review_required=true`） |
| GET | `.../windows` | 已分析窗口与成本 |
| GET | `.../reviews` | 审核事件 |
| POST | `.../reviews` | 追加审核决定 |
| POST | `.../cancel` | 取消排队/运行中的任务 |

创建请求体：

```json
{
  "observation_id": "案件内的目标观察 ID",
  "clip_id": "案件内已登记录像段 ID",
  "offset_seconds": 1.5,
  "segment_seconds": 6.0,
  "gap_seconds": 2.0,
  "max_windows": 6,
  "budget_frames": 3000
}
```

服务端派生并冻结：摄像头名称、`start_local`、OSD 当日秒、锚点秒、时钟质量（固定 `uncalibrated`）。浏览器不能提供模型路径、绝对文件路径或外部 URL。

## 4. 安全与语义不变量

1. 跨案件一律 404，不泄露“是否存在”。
2. 观察、录像段、摄像头名称都必须属于该案件；录像段必须已匹配摄像头（`match_status` 以 matched/suggested 开头）。
3. 候选只能由 `candidates_from_scores` 产生，默认 `weak_candidate` 或 `candidate`，**永远不会**写成 `confirmed`。
4. 只有人工审核事件能改 `identity_status`；撤销也是新事件。
5. `anchor_json.clock_quality` 固定 `uncalibrated`，取帧偏移是“请求的定位点”，窗口记录 `seek_drift_seconds`。
6. 任务失败写入 `failed + error_code`，不让 worker 崩溃。

## 5. 执行流程

1. worker 取最早 `queued` 任务，置 `running`、`attempt+1`。
2. 从案件内所有带摄像头名的 clip 规划窗口：以锚点秒 + `gap_seconds` 为起点，按镜头排序（锚点镜头最后），每镜头一个窗口，受 `max_windows` 限制。
3. 对每个未完成窗口：`extract_window_frames` 从真实视频按 fps 取帧到 `storage/tracking_runs/{run_id}/...`；`analyze_window` 复用 D-FINE + ByteTrack；OSNet 对每条轨迹与锚点 ROI 计算相似度；`candidates_from_scores` 产出候选。
4. 窗口、候选、进度在同一事务提交；重复执行会跳过已分析窗口（幂等）。
5. 结束状态：有候选 → `awaiting_review`；无候选 → `unresolved`；预算用尽 → `budget_exhausted`；异常 → `failed`。

审核语义：approve 将候选改为 `human_confirmed` 并把任务重新排队以继续搜索；reject 改为 `human_rejected`；revoke 回到 `candidate_unverified`。

## 7. 已知局限（B8-C 之前必须解决或继续登记）

| 局限 | 影响 | 下一步 |
| --- | --- | --- |
| 窗口规划还未接 M6 空间候选/通行时间，按镜头名排序 + 固定间隔 | 搜索顺序不是最优，可能浪费预算 | B8-C 接 `m6_directed.plan_windows` 与地图 revision |
| OSD 只有当日秒、无日期 | 跨日回放会错位 | 用 clip 日期补全绝对时间，或限制同日 |
| 取帧是请求 seek，未校验 PTS/OSD | 时间窗可能偏移几百毫秒 | 记录 drift；后续用首帧 OSD 校验 |
| 真实 analyzer 需要本地 D-FINE/OSNet 权重 | 无模型时任务 `failed: *_unavailable` | 部署检查 + 明确错误码 |
| 前端仍用模拟状态 | 用户还不能在界面发起 | B8-C |

## 8. 复现

```bash
docker exec trajnexa_s2 sh -lc "cd /srv/app && python -m pytest tests/test_m6_tracking_runs.py tests/test_m6_recording_source.py -q"
```

创建任务（curl，示例 ID 需替换）：

```bash
curl -X POST http://127.0.0.1:8000/api/v1/cases/<case_id>/tracking-runs \
  -H 'Content-Type: application/json' \
  -d '{"observation_id":"<obs>","clip_id":"<clip>","offset_seconds":1.5,"max_windows":2}'
```

worker 进程（`backend/app/worker.py`）会自动领取并执行。
